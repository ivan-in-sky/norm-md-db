# 01 · Архитектура и формат канонического Markdown

**Финальная редакция: 2026-10-23.** Спецификация проверена на четырёх реальных
документах базы (`база/документы/`) — примеры сняты с них.

## 1. Цели формата

1. **Читаемость человеком** в любом Markdown-вьювере (GitHub, VS Code, MkDocs) без плагинов.
2. **Машиночитаемость**: каждый смысловой элемент имеет метку (пункт, таблица, формула, рисунок, примечание), по которой его можно извлечь, не «понимая» текст.
3. **Прослеживаемость**: из любого куска текста понятно, из какого источника, какой версии и с какой уверенностью он получен.
4. **Стабильность идентификаторов**: `doc_id` и номер пункта не меняются между пересборками — на них ссылаются индексы, ответы агентов и закладки пользователей.
5. **Расширяемость без миграции**: новые поля метаданных не ломают старые потребители.

## 2. Именование

```
doc_id     = <kind>-<number-slug>[-<year>]
kind       = sp | snip | gost | gost-r | rd | mds | vsn | tsn | posobie | sto | fer | gesn | ter | sn | rm | ost | tu | sanpin
number-slug= номер с заменой «.» и «/» на «-»

примеры:
  СП 63.13330.2018            → sp-63-13330-2018
  ГОСТ Р 57345-2016           → gost-r-57345-2016
  СНиП 2.01.07-85*            → snip-2-01-07-85
  РД-11-06-2007               → rd-11-06-2007
  МДС 12-29.2006              → mds-12-29-2006
```

**Два имени у каждого документа.** `doc_id` (латиница) — машинный ключ:
фронтмэттер, каталог, chunk_id, имена sidecar-файлов и ассетов. **Имя заметки**
(кириллица) — то, как документ виден человеку и Obsidian: обозначение как есть,
`СП 22.13330.2016.md`. Вики-ссылки в текстах используют беспроигрышные алиасы
(`[[СП 22.13330]]`) и резолвятся на актуальную редакцию через `aliases` +
`актуальные-версии.yaml` (см. `10-local-agent.md` §7).

Файлы (в рабочем vault `md/` = `документы/`; фактические имена — в `база/документы/`):

```
документы/<Обозначение>.md            канонический текст (имя = designation кириллицей)
документы/<Обозначение>.qa.json       отчёт о качестве (машиночитаемый)
документы/<Обозначение>.qa.md         чек-лист ручной доработки (человекочитаемый)
документы/<Обозначение>.tables.jsonl  нормализованные таблицы (по одной на строку)
документы/<Обозначение>.pages.json    привязка пунктов к страницам издания
документы/<Обозначение>.assets.json   манифест ассетов: sha256, размер, alt, тип (docx-путь)
документы/<doc_id>.assets/<doc_id>-NNN.png|wmf|svg   изображения (латиница — безопасные имена)
документы/_reports/                   dashboard.md/json + отчёты сверки <doc_id>-vs-*.md
```

Sidecar-файлы именуются **по имени заметки** (кириллица), каталог картинок —
по **doc_id** (латиница): ассеты извлекаются до того, как обозначение
распознано, и их имена должны быть переносимы между системами.

Почему рядом, а не в отдельных каталогах: документ со всеми своими производными переносится/удаляется одной операцией, `git log -- 'документы/СП 22*'` показывает всю историю, а в CI удобно проверять комплектность.

Ниже — **фактический** контракт (снят с реальной заметки `СП 56.13330.2021.md`,

(`designation`, `kind`, `language`, `source`, `conversion`, `stats`).

падать на их отсутствии. Схема — в `repo-template/schemas/frontmatter.schema.json`.

## 4. Разметка тела документа

### 4.0 Принципы: только валидный Markdown, ноль «магических» комментариев

Канонический файл обязан корректно отображаться **и в Obsidian, и на GitHub**, без плагинов и без артефактов в виде «мусора» в тексте. Отсюда три следствия:

1. **Никаких HTML-комментариев как носителей семантики.** `<!-- clause 8.1.6 -->` — это не Markdown: в Obsidian он виден в Source mode и в поиске, на GitHub не даёт ссылки, а в диффах создаёт шум. Семантика переехала в стандартные конструкции.
2. **Стабильные идентификаторы = block ID Obsidian.** `^c8-1-6` в конце абзаца — это одновременно (а) валидный Markdown-текст, (б) кликабельная ссылка в Obsidian, (в) машиночитаемый якорь для конвейера. Одна конструкция закрывает три задачи.
3. **HTML остаётся только там, где Markdown бессилен** — таблицы с объединёнными ячейками (`rowspan`/`colspan`) и картинки с явными размерами. Оба поддерживаются и Obsidian, и GitHub.

### 4.0.1 Матрица совместимости

| конструкция | Obsidian | GitHub | зачем |
|---|---|---|---|
| `# 8 Конструирование` | ✅ outline + `[[#…]]` | ✅ Outline/TOC + `#8-конструирование` | разделы и подразделы |
| `**8.1.6** текст… ^c8-1-6` | ✅ ссылка `[[doc#^c8-1-6]]`, подсветка блока | ⚠️ `^c8-1-6` виден как текст; якоря нет | пункты: ID + цитируемый номер |
| `$$ … $$` (LaTeX) | ✅ MathJax | ✅ MathJax (`$$` и `$`) | формулы |
| `^e012` после `$$…$$` | ✅ ссылка на формулу | ⚠️ виден как текст | ID формулы |
| `<table>` с `rowspan/colspan` | ✅ | ✅ | таблицы со слияниями |
| `^t3` отдельной строкой после подписи | ✅ ссылка на таблицу | ⚠️ виден как текст | ID таблицы |
| `> **Примечание** — …` | ✅ | ✅ | примечания |
| `[^fn1]` + определение | ✅ | ✅ | сноски |
| `<img src alt width height>` | ✅ | ✅ | рисунки с реальным размером |
| `**Рисунок 1 — …**` + `^f1` | ✅ | ⚠️ ID виден | подписи рисунков |
| YAML-фронтмэттер | ✅ properties | ✅ (скрывается при рендере) | метаданные |
| `~~~` / `` ``` ``-блоки | ✅ | ✅ | листинги, служебные вставки |

⚠️ = конструкция отображается, но не создаёт якорь. Это осознанный компромисс: **на GitHub нет синтаксиса для произвольных якорей** — якоря генерируются только из заголовков, а произвольный HTML вроде `<a id="…">` вырезается санитайзером. Поэтому точная ссылка на пункт на GitHub делается двумя другими способами (§4.9).

Про block ID из официальной справки Obsidian: идентификатор может состоять **только из латинских букв, цифр и дефисов**; для простых абзацев он ставится в конце строки через пробел, для структурных блоков (списки, цитаты, таблицы) — на отдельной строке с пустой строкой до и после; при этом «Block references are specific to Obsidian and not part of the standard Markdown format» — то есть за пределами Obsidian это просто текст, что нас и устраивает.

### 4.0.2 Соглашение об идентификаторах

| объект | префикс | пример | образование |
|---|---|---|---|
| пункт | `c` | `^c8-1-6`, `^c10-3-9` | номер пункта, `.` → `-` |
| пункт приложения | `c` + транслит | `^ca-3`, `^cv-2-1` | «А.3» → `a-3`, «В.2.1» → `v-2-1` |
| приложение | `prilozhenie` | `^prilozhenie-b` | «ПРИЛОЖЕНИЕ Б» |
| таблица | `t` | `^t3` | порядковый номер таблицы в документе |
| формула | `e` | `^e012` | порядковый номер формулы (3 знака) |
| рисунок | `f` | `^f7` | порядковый номер рисунка |

Правила: только `[A-Za-z0-9-]`, уникальность в пределах файла (проверяет линт), детерминированность (одинаковый вход ⇒ одинаковые ID), стабильность между пересборками. Если ID уже занят, конвертер добавляет суффикс `-2`, `-3` и пишет предупреждение в QA — это сигнал, что в документе дублируются номера пунктов.

### 4.1 Разделы и подразделы

```markdown
# 8 Конструирование

## 8.1 Общие требования
```

Уровень — из стиля Word (`Heading N` / `outlineLvl`), номер — из автонумерации `numbering.xml` либо из текста. Якорь GitHub-совместимый: `#8-1-общие-требования` (GitHub сохраняет кириллицу в якорях, убирает пунктуацию и заменяет пробелы дефисами).

Разделы **не** получают block ID: у них уже есть нативный якорь заголовка, который работает и в Obsidian (`[[doc#8.1 Общие требования]]`), и на GitHub (`#81-общие-требования`).

### 4.2 Пункты

```markdown
**8.1.6** Защитный слой бетона рабочей арматуры должен быть не менее 20 мм для плит толщиной до 100 мм. ^c8-1-6
```

- номер пункта — видимый текст (он и есть предмет цитирования), выделен жирным;
- `^c8-1-6` — идентификатор: Obsidian делает из него цель ссылки, конвейер — границу чанка, линт — узел для проверки непрерывности нумерации;
- пункт — **не заголовок**: он не попадает в outline (иначе в outline документа будет 1200 записей), не влияет на TOC и не ломает семантику `#`.

Многоабзацный пункт: идентификатор ставится в конце **первого** абзаца, продолжение идёт обычными абзацами до следующего `^c…`/заголовка. Чанкер и линт трактуют пункт как «от `**N**` до следующего маркера».

```markdown
**8.1.6** Защитный слой бетона должен быть не менее: ^c8-1-6

а) для рабочей арматуры плит — 20 мм;
б) для хомутов — 10 мм.
```

### 4.3 Перечисления

```markdown
а) для элементов при пролёте до 6 м — 1/200 пролёта;
б) для элементов при пролёте 6 м и более — 30 мм;
```

Литерные маркеры сохраняются как в оригинале: на них ссылаются («п. 5.2, перечисление б)»). Строки идут **подряд, без пустых строк** — тогда в Obsidian и на GitHub это один абзац с мягкими переносами, а не «рваный» список. Автонумерация Word пересчитывается, чтобы маркеры не «поехали».

### 4.4 Таблицы

```markdown
Таблица 1 — Предельные прогибы элементов

^t1

<table>
<tr><th>Элемент</th><th colspan="2">Предельный прогиб, мм</th><th>Примечание</th></tr>
<tr><td rowspan="2">Балки и плиты</td><td>при l &lt; 6 м</td><td>1/200 l</td><td>—</td></tr>
<tr><td>при l ≥ 6 м</td><td>30</td><td>но не более 1/250 l</td></tr>
</table>
```

- подпись — обычный абзац (именно её ищет человек и RAG);
- `^t1` **на отдельной строке, с пустой строкой до и после** — требование Obsidian для структурных блоков; идентификатор привязывается к подписи, что даёт ссылку «Таблица 1» целиком;
- `<table>` — единственная часть в HTML, потому что GFM-таблицы не поддерживают `rowspan`/`colspan` в принципе;
- каждая `<tr>` — на одной строке (многострочные `<tr>` ломают часть парсеров);
- нормализованная сетка (значения каждой ячейки с учётом слияний) — в sidecar `<doc_id>.tables.jsonl`, его и используют RAG и агентные вычисления. Подробности: `02-conversion.md` §3.

Если подписи у таблицы нет, конвертер пишет QA-предупреждение и оставляет один служебный комментарий `<!-- <id>: нет подписи -->` — это единственный случай HTML-комментария в теле, и он означает дефект источника.

### 4.5 Формулы

```markdown
**3.1.2** Жёсткость определяется по формуле ^c3-1-2

$$
B_{red}=\frac{M_{crc}}{\psi M_{tot}}\cdot B_{cr}
$$

^e003

где

$M_{crc}$ — момент образования трещин;
$M_{tot}$ — полный момент от внешних нагрузок.
```

- `$$…$$` рендерится и в Obsidian (MathJax), и на GitHub; внутри блока **не должно быть пустых строк** — KaTeX/MathJax на них ломают формулу, конвертер это гарантирует;
- `^e003` — на отдельной строке (структурный блок), даёт ссылку на конкретную формулу;
- «где»-блок склеен: одна строка на обозначение, без пустых строк между ними — в рендере это единый компактный абзац;
- кириллица и греческие буквы в формулах выводятся юникодом (`ψ`, `φ`), а не макросами — KaTeX/MathJax их понимают без расширений;
- уверенность конвертации каждой формулы — в `<doc_id>.qa.json` и в сводке фронтмэттера (`blocks.formulas_to_review`), а не в теле документа.

Формула-картинка, которую не удалось распознать, оформляется fenced-блоком — он виден и в Obsidian, и на GitHub, и машиночитаем:

````markdown
```formula sp-63-13330-2018-eq047
Bred=McrcψMtot⋅Bcr
```
````

### 4.6 Рисунки

```markdown
<img src="sp-63-13330-2018.assets/sp-63-13330-2018-014.svg"
     alt="Схема сечения элемента: обозначены b, h, h0, a" width="620" height="240" />

**Рисунок 8.1 — Схема сечения элемента**

^f14
```

`alt` обязателен и содержателен: это единственный способ сделать рисунок находимым семантическим поиском (заполняется vision-моделью на стадии enrich, проверяется линтом). `<img>` вместо `![]()`, потому что нужен явный размер — иначе сканы на всю страницу растягивают страницу и в Obsidian, и на GitHub.

### 4.7 Примечания и сноски

```markdown
> **Примечание** — Для элементов с пролётом более 7,5 м прогиб уточняется расчётом.

Текст пункта[^fn3]

[^fn3]: В редакции изменения № 1, введённого приказом Минстроя России от …
```

Цитата (`>`) выбрана потому, что она одинаково рендерится в Obsidian и на GitHub и визуально отделяет примечание от требования. Если примечаний несколько — они нумеруются как в оригинале («Примечание 1 —», «Примечание 2 —»).

### 4.8 Приложения

```markdown
# Приложение А (обязательное)

## А.1 Методика расчёта

**А.1.1** Расчёт выполняется по формуле … ^ca-1-1
```

Тип приложения (обязательное / рекомендуемое / справочное) попадает в метаданные чанка: для справочных приложений агент обязан делать оговорку, что это не требование.

### 4.9 Как ссылаться на пункт: три слоя

Одна и та же цель («дать ссылку на п. 8.1.6») решается по-разному в зависимости от площадки — это не костыль, а следствие ограничений рендереров.

| слой | ссылка | где работает | как получается |
|---|---|---|---|
| **1. Obsidian** | `[[СП 63.13330.2018#^c8-1-6]]`; между документами — беспроигрышный алиас `[[СП 63.13330]]` (ведёт на актуальную редакцию) | Obsidian, любой редактор с поддержкой block refs | block ID в теле файла + `aliases` во фронтмэттере |
| **2. GitHub** | `…/blob/main/md/sp-63-13330-2018.md#L412` | GitHub | номер строки из генерируемого индекса |
| **3. Веб-зеркало / MCP** | `…/sp-63-13330-2018/#c8-1-6` · `norms.get(doc_id, clause)` | MkDocs/VitePress на Pages, API | плагин рендера ставит `id` на абзац пункта |

**Слой 2 подробнее.** GitHub не умеет якоря в произвольном месте `.md`, но умеет ссылку на строку файла — это работает всегда и не зависит от содержимого. Поэтому CI генерирует `catalog/CLAUSES.md`:

```markdown
| пункт | block id | строка | GitHub | Obsidian |
| --- | --- | --- | --- | --- |
| 8.1.6 | c8-1-6 | 412 | [открыть](https://github.com/org/stroy-norms/blob/main/md/sp-63-13330-2018.md#L412) | `[[sp-63-13330-2018#^c8-1-6]]` |
```

Файл перегенерируется на каждый коммит, поэтому номера строк не устаревают. Для цитирования во внешних документах используйте ссылку на **релизный тег** (`blob/v2026.10/…#L412`) — она не поедет при последующих правках.

**Слой 3** даёт «красивые» постоянные ссылки (`#c8-1-6`) — именно их стоит давать пользователям в ответах ассистента, если сайт развёрнут.

### 4.10 Настройка Obsidian для работы с корпусом

- **Vault** = корень репозитория (или `md/` как отдельный vault, если корпус большой и не хочется индексировать `tools/`).
- **Settings → Files and links → Use [[Wikilinks]]** — оставить включённым для внутренних ссылок; для переносимости на GitHub дублируем ссылки в Markdown-формате там, где они в тексте.
- **Settings → Editor → Strict line breaks** — выключить, чтобы «где»-блоки и перечисления (строки подряд без пустых) рендерились как один абзац с мягкими переносами.
- **Математика** работает из коробки (MathJax); для `\text{}` с кириллицей и расширений типа `mhchem` нужен сниппет с MathJax-конфигом.
- **CSS-сниппет** (`.obsidian/snippets/norms.css`) — делает идентификаторы блоков почти незаметными при чтении и скрывает служебные строки:

```css
/* identifiers of blocks: тихий серый, не отвлекает */
.markdown-rendered p > .block-id,
.markdown-source-view.mod-cm6 .cm-blockid { opacity: .35; font-size: .8em; }

/* подписи таблиц и рисунков — как подписи, а не как обычный текст */
.markdown-rendered p:has(+ table),
.markdown-rendered p:has(+ img) { font-weight: 600; font-size: .95em; }

/* таблицы нормативов: компактно, с границами, без «разъезжающихся» шапок */
.markdown-rendered table { font-size: .9em; }
.markdown-rendered table th { background: var(--background-secondary); }
```

- **Полезные плагины** (опционально, корпус от них не зависит): *Omnisearch* (поиск по всему корпусу), *Dataview* (запросы к фронтмэттеру: «покажи все `status: superseded`»), *Advanced Tables* (ручная правка таблиц), *Linter* (форматирование).

### 4.11 Чего в теле документа быть не должно

| не кладём | почему |
|---|---|
| HTML-комментарии как носители семантики | не Markdown, видны в Source mode, не дают ссылок на GitHub |
| оглавление Word (TOC) | производное, с битыми номерами страниц; пересобирается рендером |
| колонтитулы и номера страниц как текст | мусор в индексе; страницы — в `pages.json` |
| служебные поля Word (`AUTHOR`, `DOCPROPERTY`) | не несут нормативного смысла |
| строки справочных систем («Документ предоставлен КонсультантПлюс», ссылки на `login.consultant.ru`) | мусор и юридический риск; факт экспорта фиксируется во фронтмэттере (`vendor`) и в QA |
| комментарии и правки Word (`w:ins`/`w:del`) | `ins` принимается, `del` отбрасывается, факт наличия — в QA |
| сканы страниц, обложки изданий | право и объём — см. `06-licenses.md` |
| wikilinks `[[…]]` **на произвольные цели** (внешние URL, заметки-не-документы) | в теле норматива допустимы только вики-ссылки на другие нормативные документы — беспроигрышные алиасы, которые ставит obsidian-слой конвертера (`[[ГОСТ 27751]]`, `[[СП 22.13330\|СНиП 2.02.01-83]]`); на GitHub такая ссылка вырождается в текст, что приемлемо |
| дубли одной картинки | дедупликация по sha256 |

Единственное осознанное исключение — парные маркеры `<!-- bibliography -->` / `<!-- /bibliography -->` вокруг списка использованных источников: они нужны чанкеру, чтобы не смешивать библиографию с нормативным текстом. В рендере их не видно ни в Obsidian, ни на GitHub. Маркеры `<!-- <id>: нет подписи -->` у таблиц означают дефект источника и тоже допустимы. Всё остальное — только стандартный Markdown и block ID.

## 5. Слои данных и их владельцы

Рабочая база — vault `база/` (русскоязычные папки); при публикации (фаза 2)
он отображается в англоязычное репо (`источники/`→`sources/`, `документы/`→`md/`,
`правки/`→`overrides/`, `каталог/`→`catalog/`, `индекс/`→`index/`).

| слой (vault) | кто пишет | кто читает | ценность |
|---|---|---|---|
| `источники/` (оригиналы + inventory.csv) | агент (скачивание) / человек | конвертер | **невозобновляемое** — хранить вечно |
| `документы/*.md` + sidecars | конвейер | все | пересобирается из источников + правок |
| `правки/` (overrides) | человек / агент через override-файлы | конвейер при пересборке | **невозобновляемое** (ручной труд) |
| `актуальные-версии.yaml` | агент (сверка реестров) + человек | конвертер, obsidian-слой | невозобновляемое (но восстанавливается сверкой) |
| `каталог/` (catalog.*, INDEX, CLAUSES) | конвейер (`catalog`, `clauses`) | люди, агенты | производное — пересобирается |
| `индекс/` (chunks.jsonl, atoms, stats) | конвейер (`chunk`) | RAG-пайплайн | кэш — пересобирается |
| эмбеддинги / векторная БД | индексатор агента | поиск | кэш — пересобирается из chunks.jsonl |

Ключевое: стрелка данных всегда идёт сверху вниз, и **ручная правка возможна
только в `правки/`**. Это единственное правило, которое удерживает систему от
деградации через год эксплуатации.
