# 04 · RAG: от Markdown к ответам, которым верят

**Финальная редакция: 2026-10-23.** Реализовано: чанкинг (`chunker.py` →
`chunks.jsonl` + атомы таблиц + статистика), `meta.refs`/`doc.references`,
указатель пунктов CLAUSES, полный набор payload-полей для фильтрации.
Фаза 2 (критерии — `07-roadmap.md` §3): эмбеддинг-индекс (Qdrant/pgvector),
гибридный retrieval-сервер, MCP, reranker, evals-харнесс. Форматы данных ниже —
фактические (сняты с `база/индекс/chunks.jsonl`).

## 1. Почему «просто нарезать по 1000 символов» не работает на нормативах

Нормативный текст — не проза. У него три свойства, ломающие наивный RAG:

1. **Смысл привязан к номеру пункта.** Фраза «не менее 30 мм» без указания, из какого пункта какого документа, бесполезна и опасна.
2. **Таблицы и формулы неделимы.** Разрезанная пополам таблица «Расчётные сопротивления бетона» даёт не ошибку, а **правдоподобную ошибку** — худший вид ответа.
3. **Контекст — это цепочка «документ → раздел → подраздел → пункт».** Запрос «защитный слой арматуры» матчится в 40 документах; правильный ответ зависит от того, *какой* документ применим (действующий, нужный класс ответственности, нужная редакция).

Отсюда — три инженерных решения: **чанкинг по пунктам**, **атомарные таблицы/формулы**, **богатые метаданные для фильтрации**.

## 2. Чанкинг (реализовано в `chunker.py`)

Правила:

| правило | причина |
|---|---|
| пункт (от `**N** …` до следующего `^c…`/заголовка) не разрезается никогда | лучше чанк на 900 токенов, чем два бессмысленных по 450 |
| таблица — отдельный чанк с `kind: table` + отдельный «атом» с плоским текстом | HTML-таблицу плохо эмбеддить, плоский текст — хорошо |
| формула `$$…$$` едет вместе с пунктом, в котором она стоит | формула без обозначений («где») бесполезна |
| «где»-блоки склеены с формулой на этапе конвертации | см. выше |
| каждый чанк начинается с «хлебных крошек» | эмбеддинг видит `СП 63.13330.2018 > 8 Конструирование > 8.1 …` — резко улучшает retrieval |
| титульный лист — отдельный чанк `kind: title_page`, **исключается из эмбеддингов** | иначе на любой запрос матчится «МОСКВА ИЗДАНИЕ ОФИЦИАЛЬНОЕ» |
| примечания не отрываются от пункта, к которому относятся | примечание часто и есть требование |
| `chunk_id` = sha1(doc_id + clause path + content)[:16] | детерминированность: повторная индексация идемпотентна, можно диффить два билда индекса |

Размеры: цель 120–700 токенов, жёсткий потолок — только для таблиц (таблица на 3000 токенов остаётся целой, но получает `oversized: true` и в эмбеддинг идёт её плоская версия + заголовок + первые строки).

### Структура чанка (фактическая)

```json
{
  "chunk_id": "46b87744cdd7adeb",
  "doc": {
    "doc_id": "gost-31937-2024",
    "designation": "ГОСТ 31937-2024",
    "kind": "gost",
    "title": "ЗДАНИЯ И СООРУЖЕНИЯ Правила обследования и мониторинга …",
    "year": 2024,
    "status": "unknown",
    "issuing_body": "Росстандарт",
    "amendments": [],
    "license": "официальный документ (ГК РФ ст.1259 п.6)",
    "language": "ru",
    "confidence": 0.816,
    "path": "база/документы/ГОСТ 31937-2024.md",
    "references": ["ГОСТ 27751", "ВСН 58-88", "…"]
  },
  "breadcrumb": ["5 Обследование технического состояния зданий", "5.1 Общие требования"],
  "clause": "5.1.4",
  "clauses": ["5.1.4"],
  "block_id": "c5-1-4",
  "anchor": "",
  "pages": [23],
  "meta": { "refs": ["ГОСТ 27751", "СП 22.13330"] },
  "kind": "",
  "content": "**5.1.4** …текст пункта… ^c5-1-4",
  "text": "ГОСТ 31937-2024\n\n5 Обследование…\n\n5.1 Общие требования\n\n**5.1.4** …",
  "tokens_est": 340,
  "n_tables": 0,
  "n_formulas": 0,
  "has_image": false
}
```

`kind` ∈ {`""` (обычный), `table`, `title_page`}. Поле `text` идёт в эмбеддинг
(идентификатор блока из него вычищается — он не несёт семантики), `content` —
в контекст модели, остальное — в фильтры. Машинные ссылки для цитирования
(Obsidian `[[…#^c5-1-4]]`, GitHub `#L<строка>`) не дублируются в каждый чанк —
они берутся из `каталог/CLAUSES.jsonl` по `doc_id + clause` (единый источник,
не рассинхронизируется).

Атомы таблиц (`chunks.atoms.jsonl`) — плоское представление для эмбеддингов
и агентных вычислений:

```json
{"doc_id": "sp-22-13330-2016", "type": "table", "caption": "", "clause": "4.6",
 "breadcrumb": ["4 Общие положения"], "html": "<table>…</table>", "grid": [[…]]}
```

**`meta.refs`** — versionless-обозначения документов, на которые ссылается текст
чанка (`[[ГОСТ 27751]]` → `"ГОСТ 27751"`); ссылки на собственный документ
исключаются. Каждый документ дополнительно несёт агрегированный
`doc.references` — объединение `meta.refs` всех его чанков. Это готовый граф
для retrieval-расширения (§4) и для приоритизации верификации: самые
цитируемые документы чинятся первыми.

Про `block_id`: он же используется как **стабильный ключ** при переиндексации. Если текст пункта не изменился, `chunk_id` не меняется — индекс можно обновлять инкрементально, а не пересобирать целиком.

## 3. Метаданные как главный инструмент качества

Фильтры, которые обязаны быть в векторной БД (payload):

| фильтр | зачем |
|---|---|
| `status` ∈ {active, superseded, draft, rejected, unknown} | **никогда** не цитировать отменённое по умолчанию |
| `amendments`, `exclusions_since`, `excluded_clauses[]` | требование могло быть **исключено изменением**: пункт 10.10–10.21 СП 22.13330.2016 не действует с 08.01.2024 (Изм. N 5) |
| `kind` ∈ {sp, gost, gost-r, snip, rd, mds, vsn, tsn, posobie, fer, …} | «поищи только в СП» |
| `year`, `in_force_since`, `amendments` | «редакция, действовавшая на дату проектирования» |
| `topics[]`, `ics[]` | тематическое сужение (бетон, пожарная безопасность, основания) |
| `doc_id`, `clause`, `anchor`, `pages[]` | точное цитирование и переход к первоисточнику |
| `confidence`, `verified` | можно ли доверять без оговорок |
| `n_tables`, `has_image`, `n_formulas` | routing: «вопрос про таблицу» → искать среди атомов-таблиц |

**`status` — критичнее всего.** В строительстве половина цитируемых в старых проектах СНиП отменена, а СП обновлялись по 3–5 раз. Ответ со ссылкой на СНиП 2.01.07-85* вместо СП 20.13330.2016 — это не «неточность», это потенциально опасная рекомендация. Поэтому:

- статус синхронизируется из официальных реестров (СП — реестр ФАУ «ФЦС» Минстроя; ГОСТ/ГОСТ Р — ФГИС СТ / protect.gost.ru);
- в `overrides/<doc_id>.yaml` статус можно зафиксировать вручную с датой проверки (`status_checked`);
- CI раз в неделю сверяет статусы и создаёт issue при расхождении;
- в системном промпте агента — жёсткое правило: при выдаче требования всегда указывать обозначение, год, статус и наличие изменений.

## 4. Retrieval: что реально работает на нормативах

Чистый векторный поиск даёт посредственный результат: запрос «прогиб плиты» семантически близок к сотне мест. Рабочая схема — **гибрид + структурные сигналы**:

```
запрос
  ├─ (1) BM25/keyword по `content` и по плоскому тексту таблиц      ─┐
  ├─ (2) dense-поиск по `text` (с breadcrumb)                        ├─► RRF-слияние
  └─ (3) структурный поиск: обозначение документа, номер пункта      ─┘
             («СП 63.13330.2018 п. 8.1.6» → точный чанк, минуя векторы)
                                     ▼
                    фильтр по статусу/виду/году (payload filters)
                                     ▼
                       reranker (bge-reranker-v2-m3 / Cohere / LLM)
                                     ▼
             обязательный «контекст-расширитель»: к найденному пункту
             добавляем (а) его раздел, (б) примечания к нему,
             (в) таблицы, на которые он ссылается, (г) упомянутые в нём
             пункты других документов (граф references)
                                     ▼
                          генерация ответа + цитирование
```

Практические детали:

- **Эмбеддинги**: для русского языка хорошо работают `intfloat/multilingual-e5-large`, `BAAI/bge-m3`, `ai-forever/ru-en-RoBERTa`-семейство, `cointegrated/rubert-embeddings`. Обязательно прогоните 3–4 модели на своих evals — разница в hit@5 достигает 20–30%.
- **BM25 не отключать**: номера пунктов, марки бетона (B25), обозначения (СП 63.13330.2018), единицы — это токены, которые dense-модели путают.
- **Точный поиск по clause** — самый недооценённый канал: половина реальных запросов инженера содержит номер пункта. Реализуется как обычный индекс `clause → chunk_id`.
- **Граф ссылок** (`meta.refs` чанка и `doc.references` документа — считаются чанкером из вики-ссылок тела): если найден пункт СП, который ссылается на ГОСТ, — подтянуть соответствующие пункты ГОСТа (точное место — по `CLAUSES.jsonl`, если ссылка была с якорем `#^c…`). Это сильно повышает полноту ответа на вопросы типа «какие требования к арматуре».
- **Куда складывать**: Qdrant (payload-фильтры, hybrid, снапшоты — удобно), или pgvector + Postgres FTS (если уже есть Postgres и хочется одной БД), или Weaviate/Typesense/Meilisearch (если важен полнотекстовый поиск для людей). Для старта достаточно Qdrant в Docker + снапшоты в object storage.

## 5. Цитирование ответа (обязательное требование)

Формат ссылки в ответе агента — по ГОСТ Р 7.0.5-2008, с обязательными элементами:

```
СП 63.13330.2018 «Бетонные и железобетонные конструкции. Основные положения»
(с изменениями № 1–3), п. 8.1.6, с. 112. Статус: действует.
```

Для этого в чанке должны быть: `designation`, `title`, `amendments`, `clause`, `pages`, `status`. Все они есть в схеме выше — именно поэтому фронтмэттер такой подробный.

Плюс машинная ссылка: `https://<host>/<org>/<repo>/blob/main/md/sp/sp-63-13330-2018.md#8-1-6-защитный-слой` — кликабельный первоисточник.

Правила для агента (фиксируются в `skills/norms-citation/SKILL.md`):
- всегда указывать обозначение + год + пункт, а не «согласно СП»;
- если документ `superseded` — сказать об этом явно и дать актуальную замену;
- если требование найдено только в непроверенном документе (`verified: false`) — помечать ответ;
- если ответа в корпусе нет — сказать «в базе нет», а не додумывать;
- не пересказывать формулу словами — приводить её как есть, с обозначениями величин.

## 6. Evals: без них это не проект, а лотерея

`evals/qa.yaml` — набор вопросов с эталонами. Минимум 150–300 вопросов, собранных из трёх источников: реальные вопросы инженеров, типовые задачи проектирования, «ловушки» (вопросы про отменённые документы, про таблицы со слияниями, про формулы).

```yaml
- id: q-021
  question: Минимальный защитный слой бетона для рабочей арматуры плиты толщиной 100 мм в условиях эксплуатации A1?
  expect_docs: [sp-63-13330-2018]
  expect_clauses: ["10.3.1"]
  expect_answer_contains: ["10 мм", "20 мм"]
  forbid_docs: [snip-52-01-2003]
  difficulty: medium
  tags: [армирование, защитный-слой]
```

Метрики в CI:

| метрика | цель |
|---|---|
| retrieval hit@5 (документ) | ≥ 0.90 |
| retrieval hit@5 (пункт) | ≥ 0.75 |
| citation correctness (обозначение + пункт) | ≥ 0.95 |
| доля ответов со ссылкой на недействующий документ | ≤ 0.01 |
| доля «галлюцинаций» (требование отсутствует в найденных чанках) | ≤ 0.03 |
| доля отказов «в базе нет» на вопросах вне корпуса | ≥ 0.9 |

Прогон evals — часть CI при любом изменении чанкера, эмбеддингов или промптов. Это единственный способ заметить, что «мы улучшили конвертер и сломали поиск».

## 7. Что хранить в Git, а что нет (для RAG; публикационная фаза)

В vault та же логика: `документы/`, `правки/`, `каталог/` — данные;
`индекс/` — кэш (пересобирается `chunk`-ом); эмбеддинги — на стороне агента.

| артефакт | Git? | почему |
|---|---|---|
| `md/**.md` | ✅ | источник истины, ревьюится |
| `md/**.qa.json`, `.tables.jsonl`, `.pages.json` | ✅ | маленькие, нужны для аудита и регрессий |
| `catalog/*` | ✅ | производное, но маленькое и полезно для diff («что добавилось в корпус») |
| `overrides/*` | ✅ | ручные правки — обязательно версионировать |
| `evals/qa.yaml`, `evals/golden/**` | ✅ | это спецификация качества |
| `index/chunks.jsonl` | ❌ (`.gitignore`) | пересобирается за минуты, десятки МБ, diff бессмыслен |
| эмбеддинги / Qdrant-снапшоты | ❌ | object storage |
| `sources/*.doc` | ❌ | object storage |

CI собирает индекс и кладёт снапшот в `snapshots/<date>/` бакета + публикует в Releases. Восстановление — одна команда (фаза 2, вместе с индекс-сервером): `normconv index restore --snapshot 2026-10-16`; сейчас эквивалент — пересборка `chunk` из `документы/` и повторное эмбеддирование на стороне агента.
