## 2. Три правила, которые держат проект живым

1. **`md/` — источник истины.** Никаких параллельных «баз в Notion» и «актуальных версий на диске». Если что-то расходится с `md/`, неправда — то, что расходится.
2. **Ручные правки — только в `overrides/`.** Правка непосредственно в `.md` будет затёрта следующей конвертацией. Это правило надо написать крупно в README и проверять в CI (линтер сверяет `.md` с результатом повторной конвертации источника и падает, если были ручные правки мимо `overrides/`).
3. **Производное не ревьюится.** `catalog/`, `index/`, HTML-зеркало — генерируются. В PR-ревью человек смотрит на `md/`, `overrides/`, `tools/`, `evals/`.

## 3. README.md — что обязательно должно быть

- **что это** (одна фраза) и **для кого**;
- **как пользоваться за 30 секунд**: clone → `make index` → поиск; ссылка на MCP-сервер для агентов;
- **состав корпуса**: табличка по видам и количеству (генерируется из `catalog/`);
- **правовой статус** (кратко + ссылка на `NOTICE.md`) — первый вопрос, который зададут;
- **дисклеймер**: «не является официальной публикацией; для юридических значимых решений используйте официальные источники» — обязательно, см. `06-licenses.md`;
- **как добавить документ** и **как сообщить об ошибке**;
- **takedown-контакт**;
- статусы: `verified` / `converted` — что они значат и сколько чего.

## 4. AGENTS.md — инструкции для агентов в репозитории

Короткий файл в корне, который читают кодинг-агенты (Claude Code, Codex, Cursor и т.п.). Содержательный минимум:

```markdown
# AGENTS.md

Этот репозиторий — корпус нормативных документов строительства в каноническом Markdown.

## Жёсткие правила
- Не редактируй файлы в `md/` вручную: они генерируются из `sources/` конвейером `normconv`.
  Правки метаданных — в `overrides/<doc_id>.yaml`, правки формул — в `overrides/formulas/`.
- Не редактируй `catalog/`, `index/`, `site/` — они производные (`make catalog`, `make chunk`).
- Изменил конвертер → прогони `make lint` и `make check` (регрессии по `evals/golden/`).
- Один PR = один документ или одно изменение конвертера. Не смешивай.

## Команды
  make convert JOBS=8   # конвертация sources/ → md/
  make lint             # CI-гейт, ненулевой код при ошибках
  make chunk catalog clauses   # пересборка производных (чанки, каталог, указатель пунктов)
  make report           # дашборд качества
  make eval             # фаза 2: RAG-evals

## Формат данных
- Канонический Markdown описан в docs/01-architecture.md; схема — schemas/frontmatter.schema.json.
- Пункты помечены block ID в конце абзаца: `**8.1.6** текст… ^c8-1-6`. Это стабильный ID (Obsidian-ссылка `[[doc#^c8-1-6]]` + якорь для конвейера) — его нельзя удалять, переименовывать или переносить в середину абзаца.
- Таблицы, формулы и рисунки тоже имеют ID: `^t3`, `^e012`, `^f7`. Правила совместимости с Obsidian и GitHub — в `docs/01-architecture.md` §4.
- Таблицы — HTML с rowspan/colspan + нормализованная сетка в `<doc_id>.tables.jsonl`.
- Формулы — `$$…$$` LaTeX; рядом может быть комментарий `<!-- formula … | confidence … -->`.

## Как цитировать норму в ответе
  СП 63.13330.2018, п. 8.1.6 (с изм. № 1–3), с. 112 — статус: действует.
Никогда не цитируй документ со статусом superseded без явной оговорки.

## Куда смотреть при вопросах
  docs/02-conversion.md  — как устроена конвертация и что делать с «трудными» элементами
  catalog/INDEX.md       — что есть в корпусе и что требует доработки
  skills/                — готовые сценарии работы с корпусом
```

## 5. Навыки (skills) для агентов — самая недооценённая часть

Навык = папка с `SKILL.md` (frontmatter `name` + `description`, дальше — инструкция) и, опционально, скриптами. Это формат Agent Skills, который понимают современные ассистенты; но даже если ваш стек его не поддерживает, те же файлы работают как «документация для промпта» — их просто подмешивают в контекст.

Ценность навыков здесь в том, что они кодируют **предметную дисциплину**, которой у модели нет: как искать в нормативах, как проверять применимость, как цитировать, как работать с таблицами приложений.

### Набор (6 навыков — материализованы в `repo-template/skills/`)

| навык | когда подключается | что даёт |
|---|---|---|
| **norms-search** | любой вопрос по нормам | алгоритм поиска: сначала точное обозначение/пункт → BM25 → dense → фильтр по статусу → расширение контекста разделом и примечаниями |
| **norms-citation** | формирование ответа | формат ссылки по ГОСТ Р 7.0.5, обязательные элементы, правила для отменённых документов, маркировка «не проверено» |
| **norms-currency** | «действует ли…» | как проверить статус: `catalog` → `overrides` → реестр ФЦС/ФГИС СТ; как трактовать изменения №N; что делать с переходными положениями |
| **norms-compliance-check** | «соответствует ли решение требованиям» | процедура: определить объект регулирования → найти применимые документы (по `topics`, `kind`) → собрать требования по пунктам → таблица соответствия → указать, что не покрыто базой |
| **norms-tables** | вопросы про значения из таблиц | как читать `<table>` с rowspan/colspan, как использовать `.tables.jsonl`-сетку, когда брать CSV из приложений, правило «никогда не интерполируй значения из таблицы» |
| **add-document** | пополнение корпуса | пошаговый сценарий: положить в `inbox/` → конвертация (`make convert`) → прочитать `.qa.md` → закрыть review-пункты через `overrides/` → PR; для vault — мастер-алгоритм `10-local-agent.md` §3 |

### Пример: `skills/norms-citation/SKILL.md`

```markdown
---
name: norms-citation
description: Формат и правила ссылок на нормативные документы строительства
  (СП, ГОСТ, СНиП, РД) в ответах. Использовать всегда, когда ответ опирается
  на нормативное требование.
---

# Цитирование нормативных требований

## Обязательный формат
    <обозначение> «<название>», п. <номер>[, с. <страница>]
    (<статус>[, с изменениями № …])

Пример:
    СП 63.13330.2018 «Бетонные и железобетонные конструкции. Основные положения»,
    п. 8.1.6, с. 112 (действует, с изм. № 1–3)

## Правила
1. Никогда не пиши «согласно СП» без обозначения и года.
2. Если у документа `status: superseded` — укажи это явно и дай замену из
   поля `superseded_by`. Требование из отменённого документа можно приводить
   только если вопрос про исторический объект.
3. Если `verified: false` или `confidence < 0.95` — добавь оговорку
   «по непроверенной конвертации, сверьте с официальным источником».
4. Формулы приводи в LaTeX как в источнике, с расшифровкой обозначений
   из «где»-блока. Не пересказывай формулу словами.
5. Значения из таблиц приводи с указанием строки и колонки (названием, а не
   номером): «Таблица 8.1, колонка „Класс бетона B25“, строка „Rb“».
6. Если в корпусе нет ответа — так и скажи. Не выдумывай номера пунктов.
7. Давай кликабельную ссылку на первоисточник:
   <repo-url>/blob/main/md/<path>#<anchor>

## Проверка перед отправкой
- [ ] у каждой ссылки есть обозначение + год + пункт
- [ ] статус документа сверен с catalog
- [ ] нет требований из superseded без оговорки
```

### Как это работает технически

- в репозитории навыки лежат как обычные папки → версионируются вместе с корпусом;
- для агентов с поддержкой skills — подключаются нативно (локально или через `.claude/skills`, `agents/skills` — зависит от стека);
- для остальных — системный промпт RAG-ассистента ссылается на них напрямую; отдача навыков как MCP-resources (`norms://skill/citation`) — фаза 2 вместе с `tools/serve_mcp.py`;
- в CI — проверка, что `description` навыков не длиннее лимита и что навыки не противоречат `AGENTS.md` (простой линтер).

## 6. CI/CD: что должно запускаться автоматически (фаза 2)

В `repo-template/.github/workflows/` готовы два workflow: `convert.yml`
(авто-PR из `inbox/`) и `quality.yml` (lint + golden + evals). Остальные —
при публикации:

| workflow | триггер | что делает | падает, если |
|---|---|---|---|
| `convert.yml` ✅ | push в `inbox/` или `sources/`, schedule | нормализация → конвертация → открытие PR с QA-сводкой | конвертация упала |
| `quality.yml` ✅ | каждый PR / изменения `tools/` | `normconv lint` + схемы + golden-регрессии + evals | есть errors / diff эталонов / метрики ниже порогов |
| `status-sync.yml` 🔧 | еженедельно | сверка статусов с реестрами, обновление `overrides`, issue при расхождениях | — |
| `catalog.yml` 🔧 | мерж в `main` | пересборка `catalog/`, `INDEX.md` и `CLAUSES.md`, коммит ботом | — |
| `publish.yml` 🔧 | мерж в `main` + теги | сборка `tar.zst`-артефактов в Releases, публикация статического сайта, снапшот индекса в бакет | — |

Для приватного/self-hosted варианта то же самое реализуется в Gitea Actions / GitLab CI; логика идентична.

## 7. Зеркала доступа (чтобы корпусом реально пользовались)

Текущий доступ (реализован): Obsidian-vault + grep + `chunks.jsonl`/CLAUSES
(эмбеддинги на стороне агента). Остальное — фаза 2 после публикации:

| зеркало | для кого | как |
|---|---|---|
| **Obsidian-vault / GitHub web** | все | из коробки: Markdown + таблицы + KaTeX |
| **Полнотекстовый поиск** | люди | 🔧 Meilisearch/Typesense по `md/`, обновление по webhook |
| **Статический сайт** | люди, которым нужен поиск и навигация | 🔧 MkDocs Material или VitePress; публикация через GitHub Pages / свой nginx |
| **MCP-сервер** | агенты | 🔧 `tools/serve_mcp.py`: search / get / status / cite |
| **HTTP API** | интеграции (BIM, сметы, 1С) | 🔧 FastAPI поверх Qdrant + catalog, авторизация по токену |
| **Telegram-бот** | инженеры «в поле» | 🔧 тонкая обёртка над тем же API |

Рекомендация: после публикации начните с **GitHub web**, сайт/MCP/бот добавьте,
когда появится 3–5 реальных пользователей и станет понятно, чего им не хватает
(критерии — `07-roadmap.md` §3, пп. 4, 6).
