# 02 · Конвертация: как сделать это пакетно и не сойти с ума

**Финальная редакция: 2026-10-23.** Всё описанное проверено на четырёх
реальных документах базы; точные команды полного цикла — `10-local-agent.md`
(§6 и Приложение B), статус реализации каждого элемента — §12.

## 0. Главный принцип

> **Конвертация — это не «один проход», а конвейер с измеряемым качеством.**
> Каждый документ на выходе получает числовую уверенность и список конкретных мест,
> которые нужно проверить человеку. Без этого пакет из 2000 документов превратится
> в 2000 тихих ошибок, которые вылезут уже в ответах агента.

Второй принцип: **канонический Markdown — единственный источник истины**. Всё остальное (чанки, индексы, каталог, HTML-зеркало) — производные артефакты, которые пересобираются одной командой и в Git не хранятся. Это спасает от рассинхрона «md говорит одно, индекс — другое».

Третий принцип: **детерминизм**. Одинаковый вход + одинаковая версия инструмента ⇒ байт-в-байт одинаковый выход (кроме таймстемпа). Тогда `git diff` показывает реальные изменения документа, а не шум конвертера.

## 1. Сначала — инвентаризация источников (это важнее, чем кажется)

Нормативные документы приходят в трёх качественно разных видах. От вида зависит всё: стоимость, качество, очерёдность.

| Уровень | Источник | Что делать | Качество | Стоимость |
|---|---|---|---|---|
| **A1. Идеальный** | Официальная публикация в XML/UZ (формат публикационной версии по приказу Росстандарта) | детерминированный трансформатор XML → MD, **без OCR и без угадывания** | ★★★★★ | низкая |
| **A2. Реальный** | Официальная публикация в PDF (реестр СП ФАУ «ФЦС»: `api.faufcc.ru/api/assets/<uuid>`; Минстрой; ФГИС СТ) | **эталон для сверки + номера страниц**, а не источник текста (см. §9.1) | ★★★★☆ как эталон | низкая |
| **B. Рабочий** | `.doc` / `.docx` с живым текстом (ваш случай) | конвейер normconv (см. ниже) | ★★★★☆ | средняя |
| **C. Худший** | скан-PDF, фотокопии, «doc, собранный из PDF» | OCR + layout-модель, затем обязательная верификация | ★★☆☆☆ | высокая |

**Рекомендация:** начните с B (что уже есть на руках), но сразу спроектируйте формат так, чтобы A подключился без переделки. Для A отдельно заведите адаптер `uz2md` — он даст эталонные документы, по которым можно **сверять** результаты B-конвертации (см. §8, регрессионные эталоны).

> Практический совет: прежде чем конвертировать 2000 файлов, прогоните **20 самых разных** (один СНиП 1987 года в скане, один свежий СП с формулами, один ГОСТ с огромными таблицами, один РД со схемами). На этих 20 вы увидите 95% всех типов проблем. Пакетный запуск «вслепую» по всему корпусу — самая частая и самая дорогая ошибка.

### Чек-лист инвентаризации

Для каждого пакета собирать таблицу (`источники/inventory.csv`; полный перечень
колонок и правила заполнения — `10-local-agent.md` §2.3):

```
file,sha256,size_bytes,kind,doc_id,source_level,source_tier,text_layer,
has_math_omml,has_images,tables_guess,origin_url,origin_date,
fetched_from_sandbox,license_note,notes
```

Поля заполняются зондированием (рецепт скрипта — `10-local-agent.md` §6.1):
открывает zip/PDF, считает `m:oMath`, `w:drawing`, `w:tbl`/`vMerge`/`gridSpan`,
объём текстового слоя и число изображений на страницу, классифицирует скан.

## 2. Конвейер: 6 стадий

```
источники/          _work/               документы/             индекс/ каталог/
  *.doc ──┐
  *.docx ─┼─►[1 normalize]──►[2 convert + obsidian-слой]──►[3 lint/QA/compare]
  *.pdf ──┘        │                │                          │
   (со слоем)      │                │                          ├─►[4 enrich: правки/, статусы, страницы]
   (скан B/C)──► OCR (фаза 2,       │                          ├─►[5 derive: chunks, catalog, CLAUSES]
                   docs/09)         │                          └─►[6 serve: Obsidian/grep/эмбеддинги]
                                    └─ <Заметка>.md + .assets/ + .qa.json + .tables.jsonl + .pages.json
```

**[1] NORMALIZE.** `.doc` → `.docx` через `soffice --headless --convert-to docx`
(`cli convert` делает это сам, если LibreOffice в PATH). Это единственный
бесплатный надёжный путь (Word-automation через COM — только Windows;
`antiword`/`catdoc` теряют таблицы и формулы).
⚠️ Важная ловушка: при конвертации старого бинарного `.doc` **формулы OMML могут
превратиться в картинки**. Поэтому после нормализации нужно сравнить количество
`m:oMath` до/после (зондирование — `10-local-agent.md` §6.1) и, если формулы
пропали, — либо достать `.docx` из другого источника, либо пойти по пути
«формула = картинка + очередь `08-wmf-formulas.md`» (§4.2).

**[2] CONVERT.** Детерминированное преобразование в канонический Markdown:
`normconv.docx2md` для OOXML, `normconv.pdf2md` для PDF с текстовым слоем.
Сразу внутри стадии — **obsidian-слой** (`obsidian.py`): вендор-очистка,
маркеры изменений, имена заметок кириллицей, алиасы, вики-ссылки на актуальные
редакции через реестр. Разбор по элементам — в §3–§6.

**[3] LINT + QA-ТРИАЖ + СВЕРКА.** Механические проверки (`normconv.lint`,
гейт `error: 0` — коды и действия в `10-local-agent.md` §8.1) + отчёт
конвертера (`.qa.md` — чек-лист ручной доработки) + сверка с эталоном
(`normconv.compare`: покрытие пунктов, числовые значения, перенос страниц
издания; §9.1).

**[4] ENRICH.** То, чего нет в самом файле: актуальный статус действия, чем
заменён, тематические теги, ICS/ОКПД, объяснённые расхождения сверки. Часть —
парсингом реестров (ФАУ «ФЦС» для СП, ФГИС СТ/protect.gost.ru для ГОСТ), часть —
ручными файлами `правки/` (`<doc_id>.yaml`, `символы-<doc_id>.yaml`,
`сверка-<doc_id>.yaml` — форматы в `10-local-agent.md` §2.4), которые
применяются при пересборке (`--meta-override`, `--glyphs`, `--explained`).

**[5] DERIVE.** Каталог (`catalog`), указатель пунктов (`clauses`), чанки и
«атомы» таблиц (`chunk`), дашборд (`report`). Всё пересобираемое.

**[6] SERVE.** Как это читают люди и агенты — Obsidian/grep сейчас;
MCP-сервер/сайт — фаза 2 (`04-rag.md`, `05-repo-structure.md`).

### Кэш и идемпотентность

В `документы/.normconv-state.json` хранится `sha256(источника) + hash(опций) +
версия инструмента → результат`. Повторный прогон по корпусу обрабатывает только
изменившееся. **Важно:** hash считается по флагам команды, а не по содержимому
override-файлов, — после правки файла в `правки/` пересборка выполняется с
`--force`. Детерминизм: одинаковый вход + одинаковые флаги ⇒ байт-в-байт
одинаковый выход кроме `converted_at` (проверено).

### Оркестрация

Текущий масштаб (документ за документом) не требует оркестратора — рабочий
набор команд vault (точный порядок — `10-local-agent.md` §3, §10):

```bash
export PYTHONPATH=tools
python3 -m normconv.cli convert <источник.docx> --out база/документы --jobs 1 \
        --registry база/актуальные-версии.yaml \
        --license "официальный документ (ГК РФ ст.1259 п.6)" --source-uri <url>
python3 -m normconv.pdf2md  <источник.pdf>  --out база/документы --registry … (тот же набор)
python3 -m normconv.compare compare|pages …          # эталон-сверка, страницы
python3 -m normconv.cli lint    база/документы       # гейт error: 0
python3 -m normconv.cli chunk   база/документы --out база/индекс/chunks.jsonl
python3 -m normconv.cli catalog база/документы --out база/каталог
python3 -m normconv.cli clauses база/документы --out база/каталог/CLAUSES.md
python3 -m normconv.cli report  база/документы       # документы/_reports/dashboard.md
```

Для публикационного репозитория (фаза 2) тот же набор оформлен как
`repo-template/Makefile` (`make convert lint chunk catalog clauses report check`).
Для ≥1000 документов и необходимости «докачивать по одному файлу» — переход на
**Snakemake**: правило `документы/{заметка}.md: источники/{…}` даёт естественный
инкрементальный пересбор и ретраи (критерий запуска — `07-roadmap.md` §3, п. 8).

## 3. Таблицы с объединёнными ячейками — самое больное

### Почему pandoc не справляется

GFM-таблицы **не поддерживают** `rowspan`/`colspan` в принципе. Pandoc при встрече со слияниями либо теряет ячейки, либо «размазывает» содержимое, либо переключается на grid-таблицы, которые никто из RAG-парсеров не понимает. Для нормативов это критично: таблицы СП/ГОСТ почти всегда имеют многоуровневые шапки со слияниями («Предельный прогиб, мм» поверх двух колонок «при l < 6 м» / «при l ≥ 6 м»).

### Решение: три представления одной таблицы

1. **HTML `<table>` с `rowspan`/`colspan` — в самом Markdown.** Без потерь, рендерится на GitHub, понимается LLM, парсится любым HTML-парсером. Каждая строка `<tr>` — на одной строке текста (иначе часть Markdown-парсеров ломается).
2. **Нормализованная прямоугольная сетка — в sidecar `<doc_id>.tables.jsonl`.** Одна JSON-запись на таблицу: `caption`, `n_rows`, `n_cols`, `spans[]`, `grid[][]` (значение каждой ячейки с учётом наследования от объединённой), `repeat_header`. Это то, что реально нужно RAG: «какое значение в колонке X для строки Y».
3. **Плоский текст таблицы — в «атоме»** (`index/chunks.atoms.jsonl`): `заголовок | строка1 | строка2`. Именно его хорошо класть в эмбеддинг и показывать модели.

Дополнительно: если таблица **без** слияний — можно дублировать её GFM-версией (опция `--tables both`), чтобы человек видел красивую таблицу в веб-интерфейсе.

```html
Таблица 1 — Предельные прогибы элементов

^t1

<table>
<tr><th>Элемент</th><th colspan="2">Предельный прогиб, мм</th><th>Примечание</th></tr>
<tr><td rowspan="2">Балки и плиты</td><td>при l &lt; 6 м</td><td>1/200 l</td><td>—</td></tr>
<tr><td>при l ≥ 6 м</td><td>30</td><td>но не более 1/250 l</td></tr>
<tr><td>Ригели</td><td>—</td><td>20</td><td>см. 3.1.2</td></tr>
</table>
```

Подпись и идентификатор `^t1` — на отдельной строке с пустой строкой до и после: Obsidian требует именно такого размещения для структурных блоков. Метаданные таблицы (размер, слияния, нормализованная сетка) уезжают в sidecar `<doc_id>.tables.jsonl` и во фронтмэттер (`blocks.tables`), а не в HTML-комментарии.

### Обязательные проверки (уже в `lint.py`)

- арифметика сетки: сумма `colspan` по строке == `n_cols`; покрытые `rowspan` позиции не дублируются;
- `<table>`/`</table>` сбалансированы, `<tr>` не разрывается переносом строки;
- нет полностью пустой первой строки (частый артефакт — пустая строка-«отступ» в Word);
- у таблицы есть подпись `Таблица N —` (иначе в чанке она станет безымянной и не найдётся);
- вложенные таблицы помечаются флагом `nested` и уходят в ручную проверку.

### Что делать с «таблицами-монстрами»

Приложения ГОСТ (например, таблицы сортов проката на 200 строк × 15 колонок) — отдельный класс:
- не резать их на чанки по строкам;
- хранить как один атом + **дополнительно** генерировать CSV (`<doc_id>.tbl004.csv`) — для агентных вычислений CSV незаменим;
- в Markdown держать HTML-версию, но для очень больших таблиц — только первые 20 строк + ссылку на CSV (иначе один документ раздувает контекст);
- в метаданных чанка писать `table_rows: 214, table_cols: 15, truncated: true`.

## 4. Формулы

### 4.1 OMML → LaTeX (нормальный случай)

Word хранит формулы в OMML (`m:oMath`). Варианты:

| способ | плюсы | минусы |
|---|---|---|
| pandoc (`-t markdown+tex_math_dollars`) | работает из коробки | нужен XSLT-стек, **нет сигнала об ошибках**: нераспознанная конструкция молча превращается в мусор |
| `latex2mathml`/MathJax обратно | точный рендер | обратное направление (LaTeX→MathML), нам нужно прямое |
| **собственный OMML→LaTeX** (реализовано в `omml2latex.py`) | полный контроль над стилем вывода (KaTeX-совместимо), **confidence на каждую формулу**, список неизвестных тегов | нужно поддерживать маппинг (~400 строк, уже написано) |

Что покрыто в конвертере: дроби (`f`, включая `lin`/`noBar`), радикалы с степенью, `nary` (сумма/произведение/интеграл с правильным `\limits`), верхние/нижние индексы (`sSup`/`sSub`/`sSubSup`/`sPre`), скобки-делители (`d` с `\left/\right`), функции (`func` → `\sin`, `\mathrm{...}` для нестандартных), акценты (`acc`, `bar`, `groupChr`), пределы (`limLow`/`limUpp`), матрицы (`m` → `pmatrix`/`bmatrix`/`vmatrix`), массивы уравнений (`eqArr` → `aligned`), `box`, `borderBox`, `phant`.

Каждая формула получает запись в `.qa.json`:

```json
{"id":"sp-63-eq012","display":true,"confidence":0.94,
 "latex":"B_{red}=\\frac{M_{crc}}{\\psi M_{tot}}\\cdot B_{cr}",
 "plain":"Bred=McrcψMtot⋅Bcr",
 "unknown_elements":["m:eqArr"],"fallbacks":["acc:chr='̆'"]}
```

**Правило:** `confidence < 1.0` или непустой `fallbacks` ⇒ формула попадает в чек-лист ручной проверки, а в Markdown рядом остаётся комментарий с «плоским» текстом, чтобы даже при ошибке LaTeX смысл был recoverable:

```markdown
$$
B_{red}=\frac{M_{crc}}{\psi M_{tot}}\cdot B_{cr}
$$
<!-- formula sp-63-eq012 | plain: Bred=McrcψMtot⋅Bcr | confidence 0.94 | REVIEW -->
```

Хранить ли MathML? Нет: ни один LLM его нормально не читает, а место занимает. Достаточно LaTeX + plain + (опционально) PNG-рендера.

### 4.2 Формулы-картинки (ваш реальный случай)

Если формула вставлена картинкой (PNG/WMF/MathType-OLE), вариантов четыре, по убыванию предпочтительности:

1. **MathType OLE-объект** → внутри often лежит и OMML, и WMF-превью. Проверить: `word/embeddings/*.bin` + `oleObject`. Если есть OMML-поток — конвертировать его (это лучший исход).
2. **LaTeX-распознавание картинки**: модели уровня GPT-4o/Claude распознают формулы в PNG в LaTeX с точностью ~90–97% на простых выражениях. Пайплайн: вырезать картинку → прогнать через vision-модель с жёстким промптом («верни только LaTeX, без пояснений») → **обязательная** верификация обратным рендером (LaTeX → MathJax/KaTeX → PNG → perceptual diff с оригиналом). Если diff большой → в ручную очередь. Это единственный масштабируемый способ, и он автоматизируется полностью.
3. **Специализированные модели**: `pix2tex`/`LaTeX-OCR`, `texify`, Nougat, `uniMERNet` — работают локально, бесплатно, на «школьных» формулах дают приемлемое качество; на ГОСТ-овских многоярусных дробях и матрицах — хуже. Использовать как дешёвый первый проход, vision-LLM — как второй.
4. **Оставить картинкой** + плоский OCR-текст в подписи. Приемлемо для формул, которые редко ищут, но плохо для RAG: формула становится «чёрной дырой».

Что реализовано: путь (4) как безопасный дефолт (`--math image`) плюс детерминированный словарь символов `--glyphs` (путь между (3) и (4): обкатан на ГОСТ 27751-2014, §4.2 ниже и `08-wmf-formulas.md` §10), плюс полный plumbing под (1)–(3): каждая картинка-формула получает запись в `.qa.json` с координатами и флагом `formula_image`, так что скрипт «догнать LaTeX по картинкам» можно написать отдельно и прогнать по уже конвертированному корпусу, не переконвертируя всё.

#### Худший случай: OMML в файле нет вообще (проверено на СП 22.13330.2016)

Экспорт из КонсультантПлюс документа с интенсивной математикой даёт файл, в котором
`m:oMath` = **0**, зато 580 WMF-картинок размером 15–55 px с `alt="Консультант Плюс"`.
Это не формулы, а **отдельные символы**, вырезанные из текста: `γ`, `φ`, `Δ`, `δ`,
подстрочные индексы. В результате пункт выглядит так:

```markdown
- относительной разностью просадок <img src="….wmf" alt="Консультант Плюс" width="54" height="26" />
  (*L* — расстояние между точками…);
```

То есть символ потерян для поиска и для чтения моделью, но структура текста цела.

Что важно знать, прежде чем выбирать способ восстановления:

| способ | реальность |
|---|---|
| достать OMML из файла | невозможно — его там нет |
| взять формулы из текстового слоя официального PDF | **ненадёжно**: ABBYY теряет подстрочные индексы (`Nγ` → `N`, `δ´`), т.е. формула выглядит как текст, но читается неправильно |
| конвертировать WMF → SVG/PNG и распознать vision-моделью | работает, но 580 объектов на документ; для символов 15×20 px распознавание избыточно |
| **точечная ручная/автоматическая замена символов** | **лучший вариант**: символы повторяются, их десятки уникальных, а не сотни |

Практическая схема, которая получилась по факту:

1. Посчитать уникальные картинки-символы по sha256 (в СП 22 — 611 файлов, из них
   66 дублей по ссылкам).
2. Отрендерить каждый уникальный символ в PNG/SVG и **показать человеку один
   раз** — это таблица из ~50 строк «картинка → символ», а не 580 правок.
   Если есть независимая копия издания с теми же символами в текстовом слое
   (кейс ГОСТ 27751: PDF МЕГАНОРМ), словарь собирается контекстным
   сопоставлением даже без vision — и ей же верифицируется.
3. Сохранить соответствие в `правки/символы-<doc_id>.yaml` (правила
   `{sha256, find, repl, note}`) и применять на пересборке флагом `--glyphs`
   (`docx2md` и `pdf2md`). **Реализовано и обкатано**: ГОСТ 27751-2014 — 7 из 7
   символов, ноль ручных правок в теле заметки (`08-wmf-formulas.md` §10).
4. Для настоящих формул (их в СП 22 — **12 страниц из 222**, они находятся
   поиском по греческим символам в тексте официального PDF) собрать точечный
   список и выверить вручную или vision-моделью (`08-wmf-formulas.md` §5 — фаза
   2). Это десятки объектов, не сотни.

Отдельная находка, которая важнее формул: **экспорт СПС может быть новее официального
издания.** В docx были Изменения N 1–5 (пункты 4.18, 10.10–10.21, 13.5 исключены
с 08.01.2024 и 28.01.2022), а официальное PDF в реестре ФЦС — исходная редакция 2016 года.
Поэтому:
* сверка с официальным изданием должна трактовать «пропавшие» пункты как разницу редакций,
  а не как потерю текста (`normconv.compare` это умеет и пишет отдельную секцию;
  необъяснимые перенумерации фиксируются в `правки/сверка-<doc_id>.yaml` и
  снимаются с гейта флагом `--explained`);
* в корпусе нужно хранить `amendments`, `exclusions_since` и `excluded_clauses` — иначе
  агент выдаст исключённое требование как действующее;
* исключённые пункты оформляются callout'ом `> [!WARNING] Пункты 10.10–10.21 исключены
  с 08.01.2024 (изменение N 5)` — он нативно рендерится и на GitHub, и в Obsidian.

**Рекомендуемая схема работы:** конвертировать корпус с `--math latex` (то, что
OMML), собрать список всех `formula_image` из QA-отчётов, прогнать по нему
vision-пайплайн (2) отдельным батчем, результаты складывать в
`правки/формулы/<doc_id>-eq<N>.yaml` (формат — `08-wmf-formulas.md` §6;
применение при пересборке — фаза 2 вместе с vision-трактом), которые затем
подставляются вместо `<img>`. Так дорогие LLM-вызовы тратятся один раз и
кэшируются по `sha256(картинки) + версия модели`.

### 4.3 Схемы, чертежи, иллюстрации

Нормативные схемы (эпюры, узлы, графики) — не «картинки», а **носители требований**. План:

- извлекать в `<doc_id>.assets/` с детерминированными именами (`<doc_id>-003.png`) и sha256 (дедупликация одинаковых картинок между редакциями — реальная экономия);
- **EMF/WMF → SVG** (LibreOffice/Inkscape headless): вектор лучше растра и для просмотра, и для будущего распознавания; растр оставлять только если вектора нет;
- подпись `Рисунок N — ...` связывать с картинкой явным маркером, чтобы RAG мог ответить «что на рисунке 3»;
- для каждой картинки генерировать **текстовое описание** (vision-LLM: «схема армирования узла, обозначены a, b, h0…») и класть его в `alt`/метаданные — иначе рисунок не находится семантическим поиском вообще;
- графики с числовыми данными (эпюры, кривые) помечать флагом `needs_data_extraction` — их иногда нужно оцифровать.

## 5. Структура текста: заголовки, пункты, нумерация

Это место, где нормативный документ ломает обычные конвертеры. В ГОСТ/СП одновременно сосуществуют:

- разделы с **автонумерацией** Word (`1 Область применения`, `3.1 Общие положения`) — в тексте номера нет, он живёт в `numbering.xml`;
- пункты с **ручным** номером в тексте (`1.1 Настоящий свод правил распространяется…`);
- перечисления `а)`, `б)`, `1)`, `2)`;
- приложения `ПРИЛОЖЕНИЕ А`, `Приложение Б (обязательное)`;
- «шапки» таблиц и подписи рисунков, которые выглядят как заголовки, но ими не являются.

### Решения

1. **Пересчёт автонумерации.** `styles.NumberingResolver` читает `numbering.xml` (abstractNum → lvl → numFmt/lvlText/start) и воспроизводит номер так, как его показал бы Word. Без этого все разделы теряют номера, а RAG теряет возможность сослаться на «пункт 5.2.3».
2. **Сверка с ручным номером.** Если в тексте номер есть и он ≠ пересчитанному → `numbering_mismatch` в QA. Это ловит рассинхрон после правок документа и после конвертации `.doc` → `.docx`.
3. **Различать «раздел» и «пункт».** Эвристика `looks_like_title()`: короткий (≤200 симв., ≤32 слов), без `;` и `:`, не более одной точки, не заканчивается точкой при длине >12 слов. Если похоже — это заголовок (`###`), если нет — это **пункт**: обычный абзац с меткой.

```markdown
### 3.1 Общие положения

**3.1.1** Прогибы элементов не должны превышать предельных значений, установленных в таблице 1. ^c3-1-1
```

Идентификатор `^c3-1-1` — это **block ID Obsidian**: валидный Markdown, кликабельная ссылка `[[doc#^c3-1-1]]` и одновременно стабильный ключ для чанкера, линта нумерации и цитирования. На GitHub он отображается как обычный текст в конце абзаца (якоря там генерируются только из заголовков), поэтому для GitHub-ссылок CI строит индекс `catalog/CLAUSES.md` со ссылками на строки файла. Полное описание трёх слоёв ссылок — в `01-architecture.md` §4.9.

4. **Уровни заголовков** берутся из стиля (`Heading N`, `Заголовок N (ГОСТ)`, `outlineLvl`), а не из количества точек в номере — иначе `3.1.1.4.2` уедет на H5 и сломает иерархию. Номер с 5+ уровнями — повод для QA-флажка.
5. **Пропуски уровней** (H1 → H3) и **дубликаты якорей** — ошибки линта, а не предупреждения.
6. **Оглавление Word не переносится.** TOC — производный артефакт; он пересобирается из заголовков на стороне рендера (`markdown-toc` / mkdocs). Перенос старого TOC даёт битые номера страниц и мусор в поисковом индексе.

## 6. Мелочи, которые решают всё

| элемент | проблема | решение в конвейере |
|---|---|---|
| **Примечания** | «П р и м е ч а н и е —» с разрядкой; несколько примечаний подряд; примечание к таблице | нормализация разрядки (`clean_text`), типизация `> **Примечание** — …`, счётчик `notes` в QA |
| **Сноски** | ссылки на сноски теряются, текст сносок уезжает в конец | `[^fnN]` + блок определений внизу; проверка линтом «используется ↔ определена» |
| **Перекрёстные ссылки** | поле `REF _Ref12345` даёт только кэш Word, часто устаревший | двухпроходная конвертация: собираем закладки Word, block ID пунктов (`^c3-1-2`) и якоря заголовков, затем подставляем ссылку на цель — `[3.1.2 Требования к…](#^c3-1-2)` для пункта, `[…](#3-1-общие-требования)` для раздела. В Obsidian такая ссылка кликабельна; на GitHub ведёт в никуда, поэтому CI дополнительно строит `catalog/CLAUSES.md` со ссылками на строки. Неразрешённая ссылка → QA-флаг + кэш Word как fallback |
| **Гиперссылки** | внешние на `docs.cntd.ru`, `base.garant.ru` — ценный граф | сохраняются как есть + собираются в `references` (фронтмэттер) → граф цитирования корпуса |
| **«где»-блоки** | после формулы идут 5–15 коротких абзацев-расшифровок | склеиваются в один блок: не рвутся при чанкинге, формула остаётся со своими обозначениями |
| **Разрядка/капс** | «У Т В Е Р Ж Д Е Н», «С О Д Е Р Ж А Н И Е» | схлопывание одиночных букв, детект «центрованный капс» → `**…**` |
| **Табы и пробелы** | ГОСТ-овские отступы табами ломают Markdown | табы → пробелы, схлопывание, `space-before-punct` фиксы |
| **Номера страниц** | критичны для цитирования в официальных ответах | см. §7 |
| **Колонтитулы/номера страниц** | попадают в текст при OCR | удаляются по регулярным шаблонам + по позиции (первая/последняя строка страницы) |
| **Титульный лист** | мусор в поисковом индексе | выделяется в отдельный чанк с `kind: title_page`, из эмбеддингов исключается |
| **Комментарии Word / правки (revisions)** | `w:ins`/`w:del` — «удалённый» текст может попасть в корпус | `ins` принимается, `del` отбрасывается, наличие комментариев → QA-флаг |
| **Скрытый текст и поля форм** | `FORMTEXT`, `MERGEFIELD` | фиксируются в review-чек-листе |
| **Кириллица в формулах** | `\text{ж}` падает в KaTeX без расширений | греческие и кириллические символы выводятся юникодом (KaTeX/MathJax их понимают), для `\text{}` подключать `mhchem`/`mathtext`-расширения на стороне рендера |

## 7. Номера страниц (необязательно, но очень полезно)

Зачем: инженеру и юристу нужно цитировать «СП 20.13330.2016, п. 5.3, с. 17». И RAG-ответ с номером страницы вызывает на порядок больше доверия.

Как (реализовано, без ручного труда):
1. Взять **официальный PDF** издания (или независимую копию с официальной
   пагинацией — PDF МЕГАНОРМ по ГОСТ дают folio в полях). Альтернатива, когда
   издания нет: сконвертировать рабочий источник в PDF
   (`soffice --headless --convert-to pdf`) — но страницы такой сборки ≠ страницы
   издания, для цитирования они годятся условно.
2. `normconv.pdf2md` эталона → `<Эталон>.pages.json` (пункт → страница).
3. `normconv.compare pages <Заметка>.md --from <Эталон>.pages.json` — матчинг
   нормализованных подстрок переносит страницы в рабочую заметку: пишет
   `<Заметка>.pages.json` и блок `pages_source:` во фронтмэттере
   (edition/matched/file). Факт: СП 56 — 211/235 пунктов, СП 22 — 624/671,
   ГОСТ 27751 — 100/135 (остальное — пункты, которых нет в эталонном издании:
   новые редакции/артефакты извлечения).

⚠️ Номера страниц зависят от издания/редакции. Поэтому `pages` привязываются к конкретному `source.sha256` эталона, а в метаданных хранится `pages_source.edition`.

## 8. Контроль качества: как понять, что конвертация удалась

### 8.1 Метрики на документ (автоматически)

| метрика | норма | что означает нарушение |
|---|---|---|
| `confidence` | ≥ 0.95 | много неизвестных элементов/ревью |
| `words_source / words_md` | 0.95–1.05 | потерялся или задвоился текст |
| `unknown_elements` | 0 | встретились конструкции, которых конвертер не знает |
| дубликаты block ID | 0 | в документе повторяются номера пунктов (или сломана генерация ID) |
| `formulas_low_confidence` | 0 | формулы надо проверить |
| `xrefs_resolved / xrefs_total` | ≥ 0.9 | битые ссылки |
| `empty_paragraphs / paragraphs` | < 0.5 | артефакт вёрстки или «PDF в doc» |
| пропуски нумерации пунктов | 0 | потерялись абзацы |
| `tables_merged` без review | 0 | таблицы со слияниями всегда проверяются |

### 8.2 Регрессионные эталоны (обязательно)

Текущий рабочий эталон — `normconv/example/`: синтетический «трудный» документ
(`make_sample_docx.py`) с полным комплектом результатов (заметка, QA, таблицы,
чанки, каталог, CLAUSES). После любого изменения конвертера: смоук-тест
(`docs/10-local-agent.md` §1.3) + пересборка одной реальной заметки и diff
(ожидание — только `converted_at`).

Для публикационного репозитория (фаза 2) заводится `evals/golden/` — 5–10
документов, сконвертированных и **вычитанных человеком**. При каждом изменении
конвертера CI сравнивает новый результат с эталоном:
- `git diff --stat` по эталонам должен быть пустым (или объяснённым в PR);
- отдельно сравниваются счётчики (`words`, `tables`, `formulas`, `spans`), чтобы поймать регрессию даже если текст совпал случайно.

Это единственная защита от ситуации «улучшил дроби — сломал таблицы».

### 8.3 Семантические evals (для RAG, не для конвертера)

`evals/qa.yaml` — 100–300 вопросов вида:

```yaml
- id: q-014
  question: Какой предельный прогиб балки пролётом 7 м по СП 999.13330.2026?
  expect_docs: [sp-999-13330-2026]
  expect_clauses: ["3.1.1"]
  expect_answer_contains: ["30", "1/250"]
  must_not_cite: [snip-2-01-07-85]     # отменённый документ
```

Прогон в CI: retrieval hit@k, точность цитирования, доля ответов со ссылкой на недействующий документ. Без этого вы не узнаете, что ваша база не отвечает на вопросы, а «что-то выдаёт».

## 9. Путь C: сканы и PDF

### 9.1 Главное правило: официальный PDF — это эталон, а не источник

Проверено на СП 56.13330.2021: официальные публикации СП лежат в реестре ФАУ «ФЦС»
в виде PDF, полученного **сканированием с OCR** (в метаданных — `ABBYY FineReader`).
Текстовый слой есть, но извлекать из него канонический Markdown целиком — плохая идея:

| что происходит при извлечении PDF | следствие |
|---|---|
| многоколоночная вёрстка, колонтитулы на каждой странице | пункты «слипаются», часть не распознаётся |
| номер в подчёркивании попадает в `<u>3.15</u>` | `# <u>3.15</u>` становится заголовком |
| одна таблица делится на несколько pipe-блоков | 19 «таблиц» вместо 10, слияния ячеек теряются |
| короткие строки объявляются заголовками | «# труда», «# 1 Следует задать класс чистоты…» |
| переносы строк рвут единицы измерения | «14\n\nм» вместо «14 м» |

Замер на реальном документе (СП 56.13330.2021, повторено 2026-10-23): официальное
издание ФЦС (65 стр.) → 211 распознанных пунктов эталона; рабочая версия из
`.docx` → 235 пунктов (пункты + нумерованные заголовки); **покрытие эталона 100%** (ни одного потерянного пункта),
11 расхождений числовых значений — артефакты переносов строк в OCR-слое эталона
(разобраны выборочно). Аналогично для СП 22.13330.2016: покрытие 98,3%, все 11
«пропавших» пунктов классифицированы как исключённые Изменениями N 4/5 —
рабочая редакция новее эталонного издания.

Поэтому схема такая:

```
официальный PDF  ──► 1) pages.json — номер страницы каждого пункта (для цитирования)
 (эталон)             2) правовые выходные данные (©, оговорка издания, «Пересмотр СП …»)
                      3) сверка рабочей версии (normconv compare)
рабочий .docx    ──► канонический Markdown (текст, таблицы, формулы, ссылки)
```

Инструменты (точные команды с полными флагами — `10-local-agent.md` §6.4 и
Приложение B):

```bash
python3 -m normconv.pdf2md источники/official.pdf --out база/_work/md-official/ \
    --license "официальный документ (ГК РФ ст.1259 п.6)" --source-uri <url>
python3 -m normconv.compare compare "база/документы/<Заметка>.md" "база/_work/md-official/<Эталон>.md" \
    [--explained "база/правки/сверка-<doc_id>.yaml"] \
    --out "база/документы/_reports/<doc_id>-vs-official.md"
python3 -m normconv.compare pages "база/документы/<Заметка>.md" \
    --from "база/_work/md-official/<Эталон>.pages.json"
```

Сверка даёт четыре сигнала, которые нельзя получить иначе:
* **покрытие пунктов** — нет ли потерь текста в рабочей версии (главный критерий;
  `compare` возвращает nonzero при необъяснённых потерях — это гейт);
* **классификация потерь** — «исключено изменением» (рабочая редакция новее
  эталона) и «объяснено» (`--explained`: перенумерации изменениями, артефакты
  извлечения эталона) не блокируют гейт, но фиксируются в отчёте;
* **расхождения числовых значений** — здесь живут опасные ошибки, требуют
  выборочной ручной сверки;
* **номера страниц** — без официального издания цитирование «п. 6.2.19, с. 44»
  невозможно.

### 9.2 Сканы без текстового слоя

Для старых СНиП/ВСН, которые существуют только в сканах (пример: копия зарегистрированного
приказа с приложенным СП — 67 стр., 19,7 МБ, **0 символов текстового слоя**):

1. **Оценка пригодности**: `pdftotext` → если осмысленный текст есть, это не скан, идём путём B (через `pdftohtml`/`docling`).
2. **OCR-layout модели**: `docling` (IBM, хорошо держит таблицы и структуру, отдаёт Markdown/JSON), `marker`, `MinerU`, `surya`. На русскоязычных нормативах 1980–90-х качество таблиц будет плохим — закладывайте ручную доработку именно таблиц.
3. **Обязательный этап**: прогон «сырого» OCR-Markdown через тот же `lint` + отдельный детектор OCR-артефактов (одиночные буквы, `0`/`О`/`о`, `З`/`3`, разорванные дефисом слова, «рваные» строки). Каждый документ получает `ocr_confidence`.
4. **Верификация**: для сканов реалистичный план — не «вычитать всё», а **вычитать выборочно**: 100% заголовков и номеров пунктов, 100% таблиц (их обычно немного), 10–20% случайных абзацев, все формулы. Это ~2–4 часа на документ вместо 2 дней.
5. Сканы и OCR-кэш хранить **вне Git** (S3/MinIO), в Git — только Markdown + `source.sha256` + ссылка на оригинал.

## 10. Ручная доработка: процесс, а не подвиг

Модель «человек вычитывает 2000 документов» не работает. Работает модель **очереди по приоритету**:

1. Каждый документ имеет `confidence` и список `review_items` с типами (`formula`, `table`, `xref`, `ole`, `image_format`, `heading`).
2. `catalog/INDEX.md` и `_reports/dashboard.md` автоматически сортируют корпус по возрастанию уверенности и группируют доработки по типам.
3. Правила приоритизации:
   - сначала документы, которые **чаще всего цитируются** другими (видно из графа `references`) — они дают максимальный эффект;
   - потом документы с малым числом review-элементов (быстрые победы, мотивация);
   - «тяжёлые» приложения-таблицы — в отдельный поток.
4. Правки вносятся **не в Markdown напрямую**, а через override-файлы
   (в vault — `правки/`, в публикационном репо — `overrides/`):
   `<doc_id>.yaml` (метаданные, `--meta-override` — реализовано),
   `символы-<doc_id>.yaml` (словарь символов-картинок, `--glyphs` —
   реализовано), `formulas/<doc_id>-eqNNN.yaml` (LaTeX формул-картинок —
   фаза 2 вместе с vision-трактом, `08-wmf-formulas.md` §6). Всё применяется
   при пересборке (`--force`). Иначе следующая конвертация затрёт ручной труд.
   Это критически важное архитектурное решение.
5. Один PR = один документ (или один тип доработки на пакет документов). Шаблон PR автоматически включает сводку QA.
6. Агент может выполнять доработки сам (см. `skills/`), но мерж — только после человеческого approve для документов с `verified: true`.

### Два ортогональных «статуса» документа

Не путать (в ранбуке и lint они разведены явно):

1. **Правовой статус действия** — поле `status:` фронтмэттера
   (`active | superseded | draft | rejected | unknown | licensed`), сверяется с
   реестрами (§4 ENRICH; `10-local-agent.md` §4, §9). Пока не сверен —
   `unknown` (warning линта `fm_status_unknown`, штатная очередь).
2. **Степень верификации конвертации** — жизненный цикл:

```
converted (автоматически, есть confidence и очередь review_items)
   → reviewed (очередь закрыта агентом/человеком, расхождения разобраны)
      → verified: true (+ verified_by/at; ставит ТОЛЬКО человек)
   → rejected (источник плохой, ищем другой)
```

Только `verified`-документы попадают в «доверенный» индекс, на который агент
ссылается при выдаче рекомендаций без оговорок. `converted`-документы тоже
индексируются, но в ответе помечаются как непроверенные (правила —
`skills/norms-citation`).

## 11. Стоимость и производительность (ориентиры)

| операция | скорость | на 1000 документов |
|---|---|---|
| `.doc → .docx` (LibreOffice, 8 процессов) | 1–4 с/док | ~30–60 мин |
| `docx → md` (normconv, 8 процессов) | 0.3–2 с/док | ~10 мин |
| lint + chunk + catalog | 0.05–0.2 с/док | ~3 мин |
| vision-LLM на формулы-картинки | 20–60 формул/мин, $0.005–0.02 за формулу | зависит от корпуса; закладывать кэш |
| OCR скана 100 стр. (docling, GPU) | 3–10 мин | — |
| ручная верификация (по чек-листу) | 20–120 мин/док | **главная статья расходов** |

Вывод: автоматическая часть бесплатна и быстра, бюджет проекта — это **верификация**. Поэтому конвейер обязан выдавать точечный чек-лист («проверь эти 7 формул и 2 таблицы»), а не «документ сконвертирован, удачи».

## 12. Статус реализации (вместо прежнего «что добавить следующим»)

### Реализовано и проверено на реальных документах

1. **Overrides при пересборке** — `правки/<doc_id>.yaml` через `--meta-override`
   (docx и pdf): любые поля фронтмэттера, включая `status/status_checked/
   verified/topics`; ручные значения побеждают автораспознавание. *(Раньше это
   был пункт №1 «на добавление» — закрыт.)*
2. **Страницы** — `pdf2md` строит собственный `pages.json`; `compare pages`
   переносит пагинацию официального издания в рабочую заметку (+ `pages_source`
   во фронтмэттере). *(Закрыт; путь «soffice → pdf» не понадобился — официальные
   PDF и так есть.)*
3. **Словарь символов-картинок** — `--glyphs` (общий для docx2md и pdf2md):
   детерминированные подстановки с провенансом по sha256, счётчиком применений
   в QA и warning при нуле применений. Обкатан на ГОСТ 27751-2014 (7/7).
4. **Детектор колонтитулов и вендорных строк в PDF** — включая скрытый
   колонтитул СПС «Кодекс» с выниманием фактов («взамен», «применяется с») в
   метаданные до удаления; markdown-обвязка колонтитулов (`**…**`, `### …`) и
   разрывы тире («ГОСТ 31937— 2024») снимаются.
5. **Объяснённые расхождения сверки** — `compare --explained`
   (`правки/сверка-<doc_id>.yaml`): перенумерации изменениями и артефакты
   эталона не блокируют гейт, но фиксируются в отчёте.
6. **Указатель пунктов** — `clauses` (CLAUSES.md/jsonl): пункт → block id →
   строка → ссылки Obsidian/GitHub.
7. **Граф ссылок для RAG** — `meta.refs` в чанках + `doc.references`
   (агрегат), считаются из вики-ссылок obsidian-слоя.
