# 03 · Где хранить: Git, объектное хранилище, индексы

**Финальная редакция: 2026-10-23.** Текущее решение (§4): рабочий vault
`база/` на локальной машине; публикационная схема — фаза 2, вариант B/D.

## 1. Сначала разделим данные на три класса

Главная ошибка — тащить всё в один репозиторий. Данные делятся по признаку «нужен ли diff и кто это читает»:

| класс | что | объём (оценка на 2000 док.) | где жить |
|---|---|---|---|
| **T — текст** | канонический `.md`, `.qa.json`, `.tables.jsonl`, каталог, overrides, skills | 100–250 МБ | **Git** (нужен diff, PR, ревью, история) |
| **A — ассеты** | картинки/схемы (PNG/SVG), рендеры формул | 1–10 ГБ | Git LFS **или** объектное хранилище + манифест |
| **S — источники** | `.doc`, `.docx`, официальные PDF, сканы, OCR-кэш | 10–100 ГБ | **только объектное хранилище** (никогда в Git) |
| **I — индексы** | векторы, `chunks.jsonl`, ES/BM25-индекс, SQLite | 0.5–5 ГБ | **нигде не хранится как источник**: пересобираемый артефакт + снапшоты в object storage |

Принцип: **в Git живёт то, что человек ревьюит; в object storage — то, что машина читает; индексы — вообще не данные, а кэш.**

Оценка объёмов (уточните на своём пакете):

```
средний документ: 40 страниц ≈ 12 000 слов ≈ 90 КБ Markdown
2000 документов  ≈ 180 МБ текста
+ QA/tables/каталог ≈ +40%   ≈ 250 МБ
картинки: 20 на документ × 150 КБ × 2000 ≈ 6 ГБ  (после дедупликации по sha256 — обычно в 1.5–2 раза меньше)
исходники .doc/.pdf: 5–50 МБ × 2000 ≈ 10–100 ГБ
векторный индекс: 120 000 чанков × 1024 dim × 4 B ≈ 500 МБ (+ overhead ≈ 1–1.5 ГБ)
```

Вывод: **текст спокойно помещается в Git** (даже с запасом), картинки — пограничный случай, исходники — нет.

## 2. Жёсткие ограничения GitHub (проверено по документации)

| ограничение | значение | следствие для нас |
|---|---|---|
| размер файла в обычном Git | **> 50 MiB — warning, > 100 MiB — push блокируется** | сканы/PDF точно не в Git |
| загрузка файла через браузер | **25 MiB** | «закинуть документ руками через веб» не получится для больших |
| размер репозитория | **рекомендуется < 1 ГБ, настоятельно < 5 ГБ** | корпус текстов (250 МБ) — ок; с ассетами (6+ ГБ) — уже на грани |
| Git LFS | бесплатная квота хранения и трафика ограничена, дальше — платные data packs | при 6+ ГБ картинок LFS станет статьёй расходов и боли |
| Releases | **общий размер и трафик не ограничиваются**, но каждый файл — в пределах лимита LFS вашего плана | отличный канал раздачи готовых сборок корпуса |
| число файлов | практический предел ~десятки тысяч на репозиторий до заметной деградации | 2000 док. × (md + qa + tables + assets-manifest) ≈ 8000 файлов + 40 000 картинок → **картинки лучше наружу** |

## 3. Четыре варианта хранения

### Вариант A. «Один публичный GitHub-репозиторий» — быстрый старт

```
github.com/<org>/stroy-norms           # md + qa + catalog + tools + skills
github.com/<org>/stroy-norms-assets    # отдельный репо под картинки (LFS)
```

**Плюсы:** ноль инфраструктуры, мгновенный доступ людям и агентам (raw URL, GitHub API, MCP-сервер GitHub), PR-ревью из коробки, бесплатный CI (Actions), сообщество может присылать документы и исправления.
**Минусы:** лимит 5 ГБ, LFS-квоты, `git clone` становится тяжёлым, юридический риск публичного размещения (см. `06-licenses.md`), история Git хранится вечно (ошибочно залитый файл надо вычищать `git filter-repo`).

**Кому:** MVP, 100–500 документов, хочется общественного вклада и видимости.

### Вариант B. «Git + объектное хранилище» — **рекомендуемый**

```
GitHub/Gitea:   md/  catalog/  tools/  skills/  overrides/  docs/   (~300 МБ)
S3/MinIO/R2:    sources/<sha256[:2]>/<sha256>.<ext>     оригиналы
                assets/<sha256[:2]>/<sha256>.png         картинки и SVG
                snapshots/<date>/chunks.jsonl.zst        снапшоты индексов
                snapshots/<date>/qdrant.tar              бэкап векторной БД
```

В Markdown вместо относительного пути — **стабильный URI** и дублирующий relative path:

```markdown
<img src="https://cdn.example.org/assets/3f/3fa9c2....png"
     data-local="sp-63.assets/sp-63-003.png"
     data-sha256="3fa9c2..." width="620" height="240"
     alt="Схема сечения элемента: обозначены b, h, h0, a" />
```

Локальная сборка (`make assets-sync`) подтягивает картинки в `md/**/**.assets/` для офлайн-работы и PR-превью; в Git они не коммитятся (`.gitignore`), а в CI — проверяется, что каждый `data-sha256` присутствует в бакете.

**Плюсы:** репозиторий маленький и быстрый, clone за секунды, LFS не нужен вообще, оригиналы версионируются content-addressable (sha256) и не дублируются между редакциями, легко масштабироваться до 100 000 документов.
**Минусы:** два хранилища вместо одного; нужен CDN/бакет и синк-скрипт; картинки не видны в PR diff.

**Кому:** всем, кто планирует больше 300–500 документов. Это основной рекомендуемый вариант.

Дешёвые реализации бакета: **Cloudflare R2** (нет платы за исходящий трафик), **Yandex Object Storage** / **VK Cloud** (если важна юрисдикция РФ), **MinIO** на своём сервере (полный контроль, бесплатно).

### Вариант C. Self-hosted Forgejo/Gitea + MinIO

Те же схемы A/B, но на своём сервере: Gitea или Forgejo (лёгкие, один бинарник, есть Actions-совместимый CI, PR, LFS из коробки) + MinIO рядом.

**Плюсы:** никаких квот и внешних юрисдикций, полный контроль, можно закрыть контур для внутреннего использования, LFS бесплатно (своё место), нет риска takedown.
**Минусы:** администрирование (бэкапы, обновления, SSO, CI-раннеры), нет «социальной» инфраструктуры GitHub, внешний доступ надо организовывать (VPN/ reverse proxy).

**Кому:** если корпус внутренний/коммерческий, если есть юридика-озабоченность по публичному размещению, или если документов > 5000 и GitHub-лимиты мешают.

### Вариант D. «Гибрид»: приватный источник + публичное зеркало

Основной репозиторий — приватный (Gitea/GitHub), в нём исходники, QA, внутренние обсуждения. Из него CI публикует **публичное зеркало** только с `verified`-документами и очищенными метаданными.

**Плюсы:** можно держать «грязную кухню» (невычитанные конвертации, спорные по лицензиям документы) внутри, а наружу отдавать только качественное; легко отзывать документы из публичного доступа.
**Минусы:** два пайплайна публикации, риск рассинхрона.

**Кому:** оптимально, если проект делает компания/сообщество и хочет и открытости, и контроля. Мой выбор для этого проекта.

## 4. Итоговая рекомендация (решение принято)

**Сейчас:** база живёт как локальный Obsidian-vault `база/` — все четыре
класса данных (T/A/S/I) в одном месте на машине владельца; оригиналы в
`источники/`, производные пересобираются командами (`10-local-agent.md` §10).
При текущем масштабе (единицы-десятки документов) этого достаточно; резервное
копирование — на уровне бэкапов машины + (при появлении git) репозиторий.

**Фаза 2 (публикация корпуса):** сценарий «500–3000 документов, и открытость,
и контроль» → **вариант D поверх B**: приватный Git (Gitea/GitHub) для текста и
метаданных + object storage (R2/MinIO) для оригиналов и картинок + публичное
зеркало только `verified`-документов. Критерии запуска и состав работ —
`07-roadmap.md` §3, п. 3; скелет публикационного репо — `repo-template/`.

| сценарий | рекомендация |
|---|---|
| «хочу попробовать на 50 документах» | **A**: один репозиторий, картинки прямо в нём (< 1 ГБ) |
| «планирую 500–3000 документов» | **B или D**: Git для текста + R2/MinIO для ассетов и оригиналов |
| «корпус внутренний, для компании» | **C**: Forgejo + MinIO на своём сервере, доступ по VPN/SSO |
| «и открытость, и контроль» | **D**: приватный main + публичное зеркало verified |

И во всех случаях: **векторный индекс — не в Git.** Он пересобирается из
`chunks.jsonl` за минуты, а снапшоты лежат в object storage. Хранить эмбеддинги
в репозитории — классическая ошибка: каждое изменение модели эмбеддингов
превращается в гигабайтный diff.

## 5. Как заливать: процесс, а не «git add .»

### 5.1 Пакетная загрузка (первичный импорт)

```bash
# 1. кладём источники в sources/ (или сразу в бакет, если вариант B)
rsync -av /mnt/norms/ sources/batch-001/

# 2. зондируем каждый файл (рецепт скрипта — 10-local-agent.md §6.1)
#    и пополняем инвентаризацию sources/inventory.csv (16 колонок)

# 3. конвертируем
make convert JOBS=8

# 4. смотрим дашборд: что упало, что с низкой уверенностью
python -m normconv.cli report md && xdg-open md/_reports/dashboard.md

# 5. lint (CI-гейт)
make lint

# 6. производные артефакты
make chunk catalog

# 7. отдельная ветка + PR на пакет
git checkout -b import/batch-001
git add md/ catalog/ sources/inventory.csv
git commit -m "import(batch-001): 214 документов, 3 требуют доработки"
git push -u origin import/batch-001
```

**Правила пакетного импорта:**
- один пакет = 50–300 документов (больше — PR невозможно ревьюить, меньше — накладные расходы);
- документы с `confidence < 0.9` **не блокируют** пакет: они мержатся со статусом `converted` и попадают в `catalog/INDEX.md` в раздел «Требует внимания»;
- документы с ошибками линта (битые таблицы, непарные `$$`) — не мержатся, уходят в `import/batch-001-fixes`;
- в описании PR автоматически вставляется сводка из `_reports/batch.md` (через CI-скрипт).

### 5.2 Поштучная загрузка (постоянный поток)

Текущий рабочий механизм (vault) — мастер-алгоритм `10-local-agent.md` §3:
файл в `входящие/` → зондирование → `источники/` + inventory → конвертация →
сверки → производные. Для публикационного репозитория (фаза 2) проектируется
обёртка:

```bash
normconv add ~/Downloads/sp-20-13330-2016.docx     # 🔧 фаза 2 (не реализовано)
# → определяет doc_id, кладёт оригинал в sources/, конвертирует,
#   создаёт ветку doc/sp-20-13330-2016, делает PR с QA-отчётом в описании
```

Альтернатива без CLI: **«папка-приёмник»**. Кладёте файл в `inbox/` (или в бакет `s3://norms-inbox/`), CI по расписанию (или по webhook) подхватывает, конвертирует и **сам открывает PR** с QA-отчётом (workflow `convert.yml` в `repo-template/` уже делает это). Для нетехнических коллег это лучший UX: никакой командной строки.

### 5.3 Обновление документа (новая редакция / изменение)

Нормативы меняются: изменения №1, №2, новые редакции. Важно не потерять историю:

- новый источник → новый `sha256` → конвертация поверх, но **в отдельной ветке**;
- в `overrides/<doc_id>.yaml` добавляются `amendments: ["1", "2"]`, `revision_date`;
- `git diff` показывает содержательные правки — их **обязательно** смотрит человек, потому что изменение №1 к СП может поменять числовое требование;
- при полной замене документа (отмена и ввод нового): старый получает `status: superseded`, `superseded_by: <doc_id>`, **остаётся в корпусе** (на него ссылаются старые проекты), но исключается из «доверенного» индекса;
- в `CHANGELOG.md` — запись вида `2026-10-16 · СП 20.13330.2016 · изменение №3 · затронуты пп. 5.3, 8.1`.

### 5.4 Коммит-конвенция

```
<тип>(<область>): <описание>

import(batch-003): 118 ГОСТ, 4 в очередь review
doc(sp-63-13330-2018): verified — вычитаны таблицы 8.1–8.4
fix(converter): vMerge-продолжения больше не создают фантомные столбцы
feat(skills): добавлен навык citation-format
chore(catalog): пересобран после batch-003
```

Типы: `import`, `doc`, `fix`, `feat`, `chore`, `eval`, `legal`. Область для `doc` — всегда `doc_id`, чтобы история документа искалась одной командой: `git log --oneline -- md/sp/sp-63-13330-2018.md`.

## 6. Организация: папки (кратко, детали в `05-repo-structure.md`)

```
stroy-norms/
├── md/                      # канонический текст — ЕДИНСТВЕННЫЙ источник истины
│   ├── sp-63-13330-2018.md
│   └── sp-63-13330-2018.assets/     # только при варианте A (картинки в Git)
├── catalog/                 # производное: jsonl / csv / yaml / INDEX.md
├── overrides/               # ЕДИНСТВЕННОЕ место ручных правок метаданных
├── sources/                 # только inventory.csv + манифесты (сами файлы — в бакете)
├── tools/                   # normconv + Makefile + Snakemake
├── skills/                  # навыки для агентов (SKILL.md + скрипты)
├── agents/                  # AGENTS.md, конфигурация MCP, промпты
├── schemas/                 # JSON Schema фронтмэттера, чанка, overrides, catalog
├── evals/                   # golden-эталоны + вопросы для RAG-evals
├── docs/                    # эта документация
├── index/                   # .gitignore: chunks.jsonl и прочее пересобираемое
└── .github/workflows/       # CI: convert-check, lint, evals, publish
```

**Плоская структура `md/` вместо дерева по тематике.** Причины: классификация нормативов спорна и меняется (один СП относится и к «бетонным конструкциям», и к «пожарной безопасности»); переименование папок ломает все ссылки и историю; `doc_id` уникален и стабилен. Тематическая навигация живёт в `catalog/INDEX.md` и в поле `topics` фронтмэттера — её можно перестраивать бесплатно.

Если очень хочется группировки — компромисс: первый уровень по **виду документа** (`md/sp/`, `md/gost/`, `md/rd/`, `md/snip/`), что стабильно и не вызывает споров.

### 6.1 Рабочий vault Obsidian (русскоязычный) — текущая схема хранения

Публикационное репо выше — англоязычное (CI, инструменты), это фаза 2.
**Рабочая база**, которую человек открывает в Obsidian и которую ведёт
локальный агент, русскоязычная и self-contained (полное описание потока и
форматов — `10-local-agent.md` §§2–3):

```
база/
├── README.md                # для человека: устройство + ТЕКУЩЕЕ СОСТОЯНИЕ базы
├── актуальные-версии.yaml   # реестр актуальных редакций и замен (СНиП→СП)
├── входящие/                # inbox: только что скачанное, до обработки (не задерживается)
├── источники/               # оригиналы навсегда (только чтение) + inventory.csv (16 колонок)
├── документы/               # заметки <Обозначение>.md + sidecars (.qa/.tables/.pages/.assets)
│   ├── <doc_id>.assets/     #   картинки (латиница)
│   └── _reports/            #   dashboard.md/json + отчёты сверки <doc_id>-vs-*.md
├── каталог/                 # catalog.{yaml,jsonl,csv}, INDEX.md, CLAUSES.{md,jsonl}
├── индекс/                  # chunks.jsonl + chunks.atoms.jsonl + chunks.stats.json (кэш)
└── правки/                  # overrides — ЕДИНСТВЕННОЕ место ручных правок
    ├── <doc_id>.yaml        #   ручные поля фронтмэттера (--meta-override)
    ├── символы-<doc_id>.yaml#   словарь символов-картинок (--glyphs)
    ├── сверка-<doc_id>.yaml #   объяснённые расхождения с эталоном (--explained)
    └── материалы/<doc_id>/  #   доказательства ручной верификации (кропы, контактные листы)
```

Соответствие при публикации: `документы/`→`md/`, `источники/`→`sources/`,
`каталог/`→`catalog/`, `правки/`→`overrides/`, `индекс/`→`index/`,
`входящие/` не публикуется (транзитная зона). Эталонные извлечения официальных
PDF (`база/_work/md-official/`, `база/_work/md22-official/`,
`база/_work/md27751-ref/`) живут в рабочей зоне vault (`_work/`, gitignore) —
это воспроизводимые производные от файлов `источники/`.

## 7. Доступ для людей и агентов

| потребитель | как получает данные |
|---|---|
| человек (чтение) | GitHub/Gitea web (Markdown рендерится, таблицы и KaTeX — тоже), либо статический сайт (MkDocs Material / VitePress), собранный CI |
| человек (поиск) | полнотекстовый поиск по зеркалу (Meilisearch/Typesense/ES), или `ripgrep` локально |
| инженер (работа с корпусом) | `git clone` + VS Code + `make` |
| агент с файловой системой | `git clone --depth 1` / sparse-checkout только `md/` + `catalog/`; `ripgrep` по `**8.1.6**` / `^c8-1-6` |
| агент через API | **MCP-сервер** или HTTP API: `search(q, filters)`, `get(doc_id, clause)`, `list_docs(kind, status)`, `citation(chunk_id)` |
| RAG-пайплайн | `index/chunks.jsonl` → эмбеддинги → Qdrant/pgvector; снапшоты из object storage |
| интеграции (1С, САПР, BIM) | HTTP API + стабильные `doc_id`/`clause` |

### Тонкий слой доступа — почему он нужен

Давать агентам «просто файлы» — работает (текущая схема: vault + grep +
`chunks.jsonl` + CLAUSES), но плохо масштабируется: агент тратит контекст на
`ls`/`grep`, не знает статусов документов и цитирует отменённые нормы. Тонкий
MCP-сервер (300–500 строк Python) поверх `chunks.jsonl` + Qdrant решает это
(фаза 2 — критерий запуска в `07-roadmap.md` §3, п. 4):

```
tools:
  norms.search(query, kind?, status?, topic?, year_min?, k=8)   → chunks с breadcrumb и статусом
  norms.get(doc_id, clause?)                                    → точный текст пункта + якорь + страница
  norms.status(doc_id)                                          → действует/отменён/чем заменён
  norms.cite(chunk_id)                                          → готовая строка ссылки по ГОСТ Р 7.0.5
  norms.changes(doc_id, since?)                                 → что менялось
resources:
  norms://catalog                                               → список документов (для планирования)
```

Плюс **навыки** (`skills/`) — инструкции, которые говорят агенту *как* думать о нормах (см. `05-repo-structure.md` §5). Сервер даёт данные, навыки дают дисциплину.

### Раздача сборок

CI собирает и публикует в **Releases** (размер не ограничен):
- `stroy-norms-md-<date>.tar.zst` — только Markdown (≈ 80 МБ на 2000 док.);
- `stroy-norms-chunks-<date>.jsonl.zst` — готовые чанки для индексации;
- `stroy-norms-catalog-<date>.csv` — каталог;
- `stroy-norms-assets-<date>.tar.zst` — ассеты (если не используете бакет).

Это самый удобный способ «дать базу другому человеку/агенту», и он же — естественный бэкап-снимок.

---

## 8. Бэкап и зеркалирование

- Git: `git push --mirror` во второй хост (GitHub ⇄ Gitea) раз в сутки по cron.
- Object storage: версионирование бакета + lifecycle-правило (хранить все версии оригиналов вечно, снапшоты индексов — 90 дней).
- Манифесты sha256 в Git — гарантия, что при потере бакета вы хотя бы **знаете**, что потеряли, и можете целенаправленно перекачать оригиналы.
- Раз в месяц — учебное восстановление: клонировать зеркало, пересобрать индекс, прогнать evals. Бэкап, который ни разу не восстанавливали, — не бэкап.
