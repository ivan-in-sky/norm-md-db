# Как участвовать

Спасибо! Корпус живёт ровно до тех пор, пока кто-то добавляет в него документы и вычитывает их.

## Три способа помочь (по возрастанию сложности)

### 1. Сообщить об ошибке

Issue → «Ошибка в документе». Обязательно укажите:

- `doc_id` (например `sp-63-13330-2018`) и номер пункта;
- что не так (число, единица, пропущенный абзац, сломанная таблица, неверная формула);
- ссылку на официальный источник и цитату из него.

Ошибки в **требованиях** (числовые значения, единицы, классы, марки) — приоритет P1, они чинятся в тот же день.

### 2. Добавить документ

1. Убедитесь, что документ — официальный нормативный акт (СП, ГОСТ, СНиП, РД, МДС, ВСН, сметные нормативы). **Не** принимаются: СТО и внутренние документы организаций, документы с грифом, сканы из коммерческих справочных систем.
2. Проверьте по `catalog/INDEX.md`, нет ли его уже в корпусе (и нет ли более свежей редакции).
3. Положите файл в `inbox/` (или откройте issue со ссылкой на официальный источник — мы скачаем сами).
4. CI сконвертирует документ и откроет PR с QA-отчётом.

### 3. Вычитать документ (самая ценная помощь)

Откройте `catalog/INDEX.md` → раздел «Требует внимания» (сортировка по возрастанию `confidence`) и возьмите документ. Дальше:

```bash
git checkout -b verify/sp-63-13330-2018
cat md/sp-63-13330-2018.qa.md      # чек-лист: что именно проверить
```

Чек-лист сгенерирован конвертером и содержит конкретные места: таблицы со слияниями, формулы с низкой уверенностью, неразрешённые ссылки, векторные картинки.

**Правило: правки вносятся не в `md/`, а в `overrides/`.**

```yaml
# overrides/sp-63-13330-2018.yaml
doc_id: sp-63-13330-2018
title: "Бетонные и железобетонные конструкции. Основные положения"
status: active
status_checked: "2026-10-16"
issued: "2018-05-24"
in_force_since: "2018-08-01"
amendments: ["1", "2", "3"]
topics: [железобетон, армирование, бетон, конструирование]
ics: ["91.080.40"]
supersedes: [snip-52-01-2003]
```

```yaml
# overrides/formulas/sp-63-13330-2018-eq012.yaml
doc_id: sp-63-13330-2018
formula_id: sp-63-13330-2018-eq012
latex: "B_{red}=\\frac{M_{crc}}{\\psi M_{tot}}\\cdot B_{cr}"
verified_by: "И. Иванов"
verified_against: "официальный PDF, с. 47"
```

Затем:

```bash
make convert DOC=sp-63-13330-2018   # пересобрать документ с учётом overrides
make lint && make check
git add overrides/ md/ && git commit -m "doc(sp-63-13330-2018): verified — таблицы 8.1–8.4, 3 формулы"
```

Когда всё проверено — добавьте в overrides `verified: true`, `verified_by`, `verified_at`.

## Приоритеты верификации

1. документы, на которые чаще всего ссылаются другие (видно в `catalog/catalog.jsonl` → `referenced_by`);
2. документы с малым числом `review_items` (быстрые победы);
3. документы по темам, которые активно используются вашей командой.

Не пытайтесь вычитать всё: реалистичная стратегия — полная верификация топ-200 самых цитируемых документов, остальные живут со статусом `converted` и доводятся по мере использования.

## Требования к PR

- один PR = один документ или одно изменение инструмента;
- коммит по конвенции: `doc(<doc_id>): …`, `import(<batch>): …`, `fix(<область>): …`, `feat(<область>): …`;
- `make lint` зелёный;
- если менялся конвертер — `make check` зелёный и в PR объяснено, почему golden-diff пуст (или почему он ожидаем);
- в описании PR — сводка QA (CI подставит автоматически).

## Чего делать не нужно

- класть в репозиторий оригиналы `.doc/.pdf`, сканы, обложки изданий — только в object storage, и только текст идёт в корпус (см. `NOTICE.md`);
- править `catalog/` и `index/` руками;
- «улучшать» текст норматива: опечатки оригинала сохраняются как есть, расхождение с официальным текстом — это ошибка конвертации, а не повод для редактуры;
- менять `doc_id` — он стабилен навсегда.

## Локальная разработка

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e "tools/[dev]"
sudo apt install libreoffice-writer      # для .doc → .docx
make convert JOBS=8
```
